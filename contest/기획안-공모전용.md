# 1. 공모전 적합 전략

## 1.1 공모전이 보는 것

공식 평가 기준은 다음과 같다.[^contest]

| 평가 | 비중 | DearBloom 대응 |
|---|---:|---|
| 공감력 | 25% | 꽃 선물 때마다 반복되는 검색·확인·문구 작성의 구체적 장면 |
| 창의성 | 25% | 꽃말 백과나 쇼핑몰이 아니라 ‘마음을 꽃으로 번역하는 과정’으로 재정의 |
| 실현 가능성 | 20% | 현재 동작하는 추천·도감·안전·편지·구매 연결 프로토타입 |
| 완성도 | 10% | 문제 → 니즈 → 서비스 → 프로토타입 → 사업·임팩트의 5장 구조 |
| 온라인 투표 | 12% | 제목과 첫 이미지에서 문제와 결과가 즉시 이해되게 구성 |
| 영상 | 5% | 실제 추천 시나리오를 3분 안에 시연 |
| SNS | 3% | 지정 방식과 해시태그에 맞춰 인증 |

## 1.2 공모전용 문제를 좁히는 방식

### 공모전 첫 장에서 피할 표현

- “국내 화훼산업이 불황이다.”
- “꽃말을 모아둔 사이트가 없다.”
- “AI로 꽃을 추천한다.”
- “화훼산업을 활성화하겠다.”

위 표현은 너무 크거나 사실을 과장할 수 있고, 사용자가 매일 느끼는 귀찮음이 보이지 않는다.

### 공모전 첫 장에서 사용할 표현

> **꽃을 선물할 때마다 꽃말, 색상 의미, 반려동물 안전성, 카드 문구와 구매처를 따로 찾는 과정이 너무 귀찮다.**

### 문제의 본질

> **꽃이 부족한 것이 아니라, 내가 전하려는 마음에 이 꽃이 정말 맞는지 판단할 기준이 부족하다.**

### 해결의 반전

> 꽃 이름부터 찾게 하지 않고, **관계와 마음부터 말하게 한다.**

## 1.3 홈글 출품작에서 가져올 설명 원칙

홈글 공모전 게시판의 잘 읽히는 제목과 소개는 다음 공통점이 있다.

1. 사용자가 바로 아는 상황을 제목에서 보여준다.
2. 기능 이름보다 해결되는 결과를 먼저 말한다.
3. 첫 문장은 “왜 불편한가”를 짧게 적는다.
4. 문제를 거창한 사회 이슈보다 개인의 반복 행동에서 시작한다.
5. 프로토타입으로 무엇을 직접 눌러볼 수 있는지 분명하게 말한다.

DearBloom도 아래 순서를 따른다.

```text
꽃을 고르려다 검색 탭이 늘어나는 장면
→ 사용자가 원하는 것은 ‘이 꽃이면 괜찮다’는 이유
→ DearBloom의 입력과 결과
→ 실제 프로토타입 시연
→ 구매와 화훼산업으로 확장
```

## PAGE 1 / 5 — 문제·배경

### 이 페이지의 목표

심사위원이 5초 안에 “나도 꽃 고를 때 이런다”고 느끼게 한다.

### 메인 헤드라인

# 꽃은 주고 싶은데,  
# 검색할수록 더 어려워집니다

### 본문 최종 카피

생일, 기념일, 감사, 위로, 사과처럼  
꽃으로 마음을 전하고 싶은 순간은 많습니다.

하지만 막상 꽃을 고르려고 하면 고민이 시작됩니다.

> “이 꽃말이 지금 관계에 정말 어울릴까?”  
> “색이 달라지면 의미도 달라지나?”  
> “상대가 고양이를 키우는데 괜찮을까?”  
> “꽃과 함께 무슨 말을 적어야 하지?”

결국 한 번의 선물을 위해 다음 과정을 반복합니다.

### 검색 과정 시각화

```text
꽃 추천 검색
→ 꽃말 재검색
→ 색상별 의미 확인
→ 반려동물 안전 확인
→ 카드 문구 검색
→ 실제 꽃집·구매처 검색
```

### 강조 문장

> **한 번의 꽃 선물에, 최소 다섯 번의 검색과 판단이 필요합니다.**

### 페이지 하단 결론

> 문제는 꽃 정보가 없는 것이 아닙니다.  
> **내 마음에 이 꽃이 정말 맞는지 판단할 기준이 없는 것입니다.**

### 시각 구성

- 좌측 55%: 메인 헤드라인과 사용자의 질문 4개
- 우측 45%: 휴대폰 검색 탭이 5~6개 쌓인 그래픽
- 하단: `꽃말 → 안전 → 문구 → 구매처` 흐름
- 산업 통계와 기능 설명은 이 페이지에 넣지 않는다.

### 사용 화면

프로토타입 화면보다 **검색 탭이 늘어나는 문제 장면**을 사용한다. 실제 휴대폰 검색 화면을 직접 캡처할 경우 개인정보와 상표 노출을 정리한다.

## PAGE 2 / 5 — 사용자 니즈·핵심 인사이트

### 이 페이지의 목표

“꽃 추천”이 아니라 **선택 확신과 표현의 문제**라는 점을 보여준다.

### 메인 헤드라인

# 사용자가 원하는 것은 더 많은 꽃이 아니라,  
# “이 꽃이면 괜찮다”는 이유입니다

### 핵심 사용자

> 꽃을 잘 모르지만, 가까운 사람에게 의미 있고 센스 있는 선물을 하고 싶은 20~30대 사용자

### 사용자 여정

| 순간 | 사용자의 생각 | 남는 문제 |
|---|---|---|
| 마음이 생김 | 사과하고 싶다 / 축하하고 싶다 | 감정을 꽃 이름으로 바꾸기 어려움 |
| 꽃을 찾음 | 예쁜 꽃은 많은데 무엇이 맞지? | 선택 기준 부족 |
| 꽃말을 확인 | 사이트마다 말이 다르다 | 신뢰와 맥락 부족 |
| 상대를 고려 | 고양이, 향, 취향은 괜찮나? | 안전과 개인화 부족 |
| 전달 준비 | 뭐라고 적어야 하지? | 표현 부담 |
| 구매 | 지금 어디서 살 수 있지? | 정보와 구매 분리 |

### 핵심 인사이트

> **꽃 고르기는 상품 검색이 아니라, 마음을 꽃으로 번역하는 과정입니다.**

### 사용자가 실제로 원하는 것

- 관계와 상황을 먼저 이해해주는 것
- 왜 이 꽃이 맞는지 설명해주는 것
- 꽃말과 안전성을 믿을 수 있는 근거
- 함께 전할 말을 자연스럽게 만들어주는 것
- 추천 후 실제 구매까지 연결해주는 것

### 사용자 인용문

> “꽃 이름을 더 많이 알고 싶은 게 아니라,  
> 이 사람에게 내 마음을 가장 잘 전할 꽃을 알고 싶어요.”

### 시각 구성

- 상단: 핵심 인사이트 한 문장
- 중단: 사용자 여정 6단계 아이콘
- 하단 좌측: 핵심 사용자
- 하단 우측: 사용자 인용문
- 텍스트는 Page 1보다 줄이고 여백을 충분히 둔다.

## PAGE 3 / 5 — 서비스 컨셉

### 이 페이지의 목표

입력부터 결과까지 DearBloom의 해결 구조를 한눈에 보여준다.

### 메인 헤드라인

# 관계와 마음을 말하면,  
# DearBloom이 꽃과 이유를 함께 고릅니다

### 서비스 한 문장

> **DearBloom은 관계·상황·취향·추억·안전 조건을 이해해, 검증된 꽃 데이터에서 성격이 다른 꽃 3안과 선택 이유를 추천합니다.**

### 핵심 흐름

```text
1. 관계와 마음 선택
        ↓
2. 상대의 취향·추억·안전 조건 입력
        ↓
3. AI가 자유로운 문장을 추천 단서로 해석
        ↓
4. 검증된 꽃말·이야기·안전 데이터가 후보 판단
        ↓
5. 꽃 3안 + 이유 + 이야기 + 메시지 + 구매처
```

### 결과 3안

| 역할 | 설명 |
|---|---|
| 안심 선택 | 관계와 상황에 가장 무난한 꽃 |
| 의미 선택 | 꽃말과 이야기가 가장 잘 맞는 꽃 |
| 대담 선택 | 상대의 취향과 추억을 더 강하게 반영한 꽃 |

### 핵심 기능 4개

#### 1. 선택 이유가 있는 추천

꽃 이름만 보여주지 않고 어떤 입력과 이야기 때문에 골랐는지 설명한다.

#### 2. 여러 갈래의 꽃말

색상·문화권·시대에 따라 달라지는 의미를 출처와 함께 보여준다.

#### 3. 안전을 먼저 보는 추천

고양이·강아지에게 크게 위험한 꽃은 점수를 낮추는 것이 아니라 추천 전에 제외하고, 가벼운 주의가 필요한 꽃은 그 사실을 함께 보여준다.

#### 4. 전달과 구매까지 연결

카드 문구, 비밀 편지, 꽃 조합, 판매처·가까운 꽃집 탐색으로 이어진다.

### 슬로건

> **하고 싶은 마음부터 고르면, 꽃과 이야기가 그 마음을 전해드립니다.**

### 시각 구성

- 왼쪽: 입력 카드 3개
  - `연인`
  - `먼저 손 내밀고 싶은 날`
  - `고양이와 살아요`
- 중앙: AI 해석 + 검증 데이터 아이콘
- 오른쪽: 꽃 결과 카드 3장
- 하단: 메시지·편지·구매 행동 아이콘

## PAGE 4 / 5 — AI 구조·프로토타입

### 이 페이지의 목표

“그럴듯한 아이디어”가 아니라 **현재 실제로 동작하며, AI를 책임 있게 사용한다**는 점을 증명한다.

### 메인 헤드라인

# AI는 마음을 읽고,  
# 검증된 데이터는 사실을 지킵니다

### 역할 분리

| AI가 하는 일 | 검증 데이터·엔진이 하는 일 |
|---|---|
| “첫눈을 함께 봤어요” 같은 자유 문장 이해 | 꽃말과 출처 확인 |
| 취향·추억·분위기 단서 추출 | 고양이·강아지 안전성 판단 |
| 추천 꽃에 맞는 자연스러운 메시지 작성 | 크게 위험한 꽃·비선호 꽃 강제 제외 |
| 사용자의 말투에 맞춰 문장 다듬기 | 관계·상황·계절·취향 점수와 3안 다양성 |

### 안전 원칙

> **사실은 데이터에서, AI는 해석과 표현에서 사용합니다.**

- AI가 출처 없는 꽃말을 만들지 않음
- AI가 반려동물 독성을 추측하지 않음
- 메시지 생성 실패 시 검토된 예문으로 폴백
- 추억과 편지 원문은 공유 URL과 분석 로그에 남기지 않음

### 현재 직접 눌러볼 수 있는 기능

- 관계·상황 기반 꽃 3안 추천
- 자유 서술을 반영한 추천 변화
- 반려동물 위험 꽃 제외
- 꽃말·나라별 의미·설화·문학 확인
- 여러 사람 각각 추천 및 단체 부케
- 카드 문구 수정·새로 받기
- 비밀 편지
- 꽃 조합기
- 366일 탄생화
- 구매처 탐색

### 프로토타입 캡처 배치

다음 4개 화면을 실제 프로토타입에서 캡처한다.

1. **추천 입력 화면**  
   관계·마음·취향 중 한 화면

2. **추천 결과 화면**  
   꽃 3안과 추천 이유가 동시에 보이는 구간

3. **이야기·안전 화면**  
   꽃 이야기 또는 반려동물 배지가 보이는 구간

4. **편지 또는 꽃 조합기**  
   결과가 실제 행동으로 이어지는 장면

### 캡처 콜아웃 문구

- `관계와 마음부터 선택`
- `크게 위험한 꽃은 추천 전 제외`
- `왜 이 꽃인지 설명`
- `꽃과 함께 전할 문장`
- `실제 구매처로 연결`

### 정적 데모 고지

공모전용 Netlify 데모는 서버 없이 동작한다.

- 추천·안전·꽃말·이야기: 실제 엔진과 데이터
- 카드 문구: API 키를 노출하지 않기 위해 미리 검토한 예문
- 본배포: 서버에서 AI 메시지 생성 가능

이 차이를 숨기지 않고 화면에서 안내한다.

# 6. 3분 발표영상 대본

## 0:00–0:20 — 문제 장면

안녕하세요. 꽃을 고르는 이유까지 추천하는 AI 서비스, DearBloom을 소개하겠습니다.

꽃을 선물하려고 검색을 시작하면 꽃 추천, 꽃말, 색상 의미, 반려동물 안전성, 카드 문구와 꽃집까지 계속 다른 페이지를 열게 됩니다.

## 0:20–0:45 — 문제의 본질

정보가 없는 것은 아닙니다. 하지만 이 꽃이 지금의 관계와 마음에 정말 맞는지 판단하기는 어렵습니다.

사용자가 원하는 것은 더 많은 꽃 이름이 아니라, **“이 사람에게는 이 꽃이면 괜찮다”는 이유**라고 생각했습니다.

## 0:45–1:10 — 서비스 정의

DearBloom은 꽃 이름보다 관계와 마음부터 묻습니다.

누구에게 주는지, 어떤 마음인지, 상대의 취향과 추억, 반려동물이나 향처럼 조심할 조건을 입력하면 성격이 다른 꽃 세 가지와 선택 이유를 추천합니다.

## 1:10–2:10 — 프로토타입 시연

지금 연인에게 먼저 손을 내밀고 싶은 상황을 선택해보겠습니다.

상대는 차분한 분위기와 보라색을 좋아하고 고양이와 함께 산다고 입력했습니다. 함께 떠오르는 장면에는 바닷가의 보라색 노을을 적었습니다.

서비스는 이 자유로운 문장에서 단서를 읽어 추천에 반영합니다. 하지만 꽃말과 안전성을 만들어내지는 않습니다.

검증된 데이터와 추천 엔진이 고양이에게 크게 위험한 꽃을 먼저 제외하고 주의가 필요한 꽃은 표시하며, 관계와 마음, 계절, 취향을 바탕으로 안심·의미·대담의 세 가지 결과를 보여줍니다.

각 결과에서는 왜 이 꽃인지, 어떤 상황에서는 피해야 하는지, 색상과 문화권에 따라 꽃말이 어떻게 달라지는지 확인할 수 있습니다.

이 꽃에 얽힌 이야기와 문학도 읽을 수 있고, 함께 전할 문장을 고쳐 쓰거나 비밀 편지로 만들 수 있습니다. 마지막에는 추천된 꽃 이름으로 실제 구매처를 찾을 수 있습니다.

## 2:10–2:35 — AI와 안전성

DearBloom의 원칙은 **사실은 데이터에서, AI는 해석과 표현에서 사용한다**는 것입니다.

AI는 사람의 자유로운 말을 이해하고 문장을 자연스럽게 만듭니다. 꽃말의 출처, 반려동물 안전성과 추천 판단은 검증된 데이터와 규칙 엔진이 담당합니다.

## 2:35–3:00 — 임팩트와 마무리

DearBloom은 꽃을 판매하는 서비스보다 먼저, 꽃을 선택할 이유를 만들어 주는 서비스입니다.

꽃을 기념일에만 사는 상품에서 감사, 위로, 응원과 화해의 일상적인 표현으로 확장하고, 추천 결과를 실제 지역 꽃집과 구매처로 연결하겠습니다.

꽃은 주고 싶은데 어떤 꽃을 줘야 할지 어려웠던 순간, DearBloom이 마음을 꽃으로 번역하겠습니다. 감사합니다.

## C. 불일치 상세 — 판단이 필요한 3건

### C-1. 「반려동물 위험 꽃 제외」는 **심각 독성만** 제외한다

카피의 표현:

- §3 핵심 기능 3 — 「고양이·강아지에게 위험한 꽃은 점수를 낮추는 것이 아니라 **추천 전에 제외한다**」
- §4 — 「반려동물 위험 꽃 제외」
- §6 대본 1:10–2:10 — 「고양이에게 위험한 꽃을 **먼저 제외하고**」
- §8 체크리스트 — 「고양이 조건에서 위험 꽃이 제외된다」

엔진의 실제 규칙(`src/lib/engine/exclude.ts`):

- `serious` · `life_threatening` → **후보에서 강제 제외**
- `mild_gi`(가벼운 위장 장애) → **제외하지 않고 주의 문구만 붙인다**

실측(§4.3 심사 동선과 같은 입력 · `반려묘와 살아요` 선택):

| 안 | 꽃 | 고양이 독성 | 화면 배지 |
|---|---|---|---|
| 안심(1안) | 흰 튤립 | `mild_gi` | **반려동물 주의 — 고양이·강아지에게 독성이 있어요** |
| 의미(2안) | 과꽃 | 없음 | 반려동물 안전 — 고양이·강아지에게 알려진 독성이 없어요 |
| 대담(3안) | 글라디올러스 | `mild_gi` | **반려동물 주의 — 고양이·강아지에게 독성이 있어요** |

제외 규칙 자체는 실제로 돈다. 같은 입력에서 **반려묘를 빼면 2안이 히아신스**(고양이 `serious`)로 나오고, **반려묘를 넣으면 히아신스가 사라지고 과꽃으로 교체**된다. 즉 심각 독성 제외는 눈으로 재현된다.

문제는 표현이다. 지금 카피대로 말한 직후 심사위원이 1안·3안을 열면 **「반려동물 주의 / 고양이·강아지에게 독성이 있어요」 배지**를 본다. 특히 1안의 화면 라벨이 `가장 안전한 선택 (안심)` 이라 「안전」이 반려동물 안전으로 읽힐 여지가 있다(원본 §3 의 정의는 「관계와 상황에 가장 무난한 꽃」이다).

→ **판단 필요.** 카피를 「심각한 독성은 추천 전에 제외하고, 가벼운 것은 주의를 함께 알린다」로 정확히 좁힐지, 아니면 시연 시나리오를 바꿀지.

### C-2. 자유 서술이 결과를 바꾸려면 **같은 정보를 칩으로 또 고르면 안 된다**

§4.3 심사 동선은 `연인 / 화해 / 차분함 / 고양이` 만 고르고 자유 서술을 적는다(색 선택 없음).
§6 영상 대본은 여기에 **「보라색을 좋아하고」를 더한다**(색 칩 선택).

두 경로를 각각 돌린 결과:

| 입력 | 3안 결과 | 단서 밴드 |
|---|---|---|
| 색 칩 없음 · 자유 서술 없음 | 흰 튤립 / 과꽃 / **재스민** | (없음) |
| 색 칩 없음 · 「바닷가의 보라색 노을」 | 흰 튤립 / 과꽃 / **글라디올러스** | 「당신이 들려준 이야기를 담아 골랐어요」 · `보라` · 바닷가의 보라색 노을 |
| **색 칩 `보라`** · 자유 서술 없음 | 흰 튤립 / 과꽃 / 글라디올러스 | (없음) |
| **색 칩 `보라`** · 「바닷가의 보라색 노을」 | 흰 튤립 / 과꽃 / 글라디올러스 | 단서 밴드는 뜸 |

즉 **색 칩을 고르지 않았을 때만 자유 서술이 3안을 실제로 바꾼다**(재스민 → 글라디올러스). 색 칩을 이미 골랐다면 자유 서술이 같은 말을 되풀이하는 셈이라 결과가 그대로고, 화면에는 단서 밴드만 추가된다.

§8 체크리스트의 「자유 서술이 결과에 반영되는 시나리오가 있다」를 **화면에서 증명하려면 §4.3 동선(색 칩 없음)을 써야 한다.** §6 대본의 「보라색을 좋아하고」를 그대로 두면 결과 변화는 보이지 않는다.

→ **판단 필요.** 영상 대본에서 색 선택을 빼고 「보라」는 자유 서술만으로 들어가게 할 것을 권한다(그러면 대본의 「AI 가 단서를 읽는다」 장면이 결과 변화로 뒷받침된다).

### C-3. 정적 데모에서 멈추는 것은 **카드 문구만이 아니다** — AI 해석 층도 함께 멈춘다

§4 「정적 데모 고지」가 적은 차이:

- 추천·안전·꽃말·이야기: 실제 엔진과 데이터
- **카드 문구**: 미리 검토한 예문
- 본배포: 서버에서 AI 메시지 생성 가능

실제로는 자유 서술을 읽는 **AI 해석 층(§1.5j)도 정적 데모에서 돌지 않는다.** `src/app/recommend/extract-cues.ts` 는 서버 전용이고 데모 빌드는 이 파일을 아예 import 하지 않는다(주석에 「데모는 이 파일을 아예 import 하지 않으므로 키가 없는 쪽 = 로컬 사전 경로가 저절로 성립한다」고 적혀 있다). 데모의 단서 추출은 전부 **로컬 사전 매칭**(`inferCuesFromTexts`)이다.

눈에 보이는 결과:

| 자유 서술 | 데모에서 읽어 낸 단서 |
|---|---|
| 「바닷가의 보라색 노을」 | `보라` (색 이름이 글자 그대로 있어 사전이 잡음) |
| 「첫눈을 함께 봤어요」 | 없음 (원문만 표시) |
| 「파도 소리를 좋아해요」 | **없음 — 단서 밴드 자체가 서지 않음** |

마지막 줄이 특히 중요하다. **§6 대본과 §5 게시글 본문이 예로 든 「파도 소리를 좋아해요」는 정적 데모에서 아무 단서도 만들지 않는다.** 저장소 주석은 바로 이 문장을 「AI 라면 calm · blue 로 옮긴다」는 예로 들고 있다 — 즉 AI 가 붙은 본배포에서만 되는 일이다.

같은 이유로 §6 의 「AI 는 이 자유로운 문장에서 **바다, 보라색, 차분함**이라는 단서를 읽습니다」도 데모 화면과 어긋난다. 화면에 실제로 서는 단서 칩은 **`보라` 하나**다.

→ **판단 필요.** ⑴ 고지 문구에 「자유 서술 해석도 데모에서는 사전 기반」을 한 줄 더할지, ⑵ 대본의 예문을 데모에서 실제로 단서가 잡히는 문장으로 바꿀지, ⑶ 영상은 본배포 화면으로 찍을지.

## F. 그 밖에 기록해 둘 것

### F-1. 도감·달력 사진이 전부 원격 CDN 핫링크다

`/flowers/*` 상단 사진과 `/calendar`·탄생화 사전 썸네일(280장)은 전부 `images.unsplash.com` · `images.pexels.com` 직접 참조다(도판 `public/plates/*.jpg` 와 탄생화 사진 `public/birth/*` 은 로컬). 시간을 충분히 주면 **280장 전부 로드**되지만(실측 깨짐 0), 빠르게 스크롤하면 일시적으로 다수가 비어 보인다. 심사위원 네트워크가 느리거나 두 CDN 이 막힌 환경에서는 그 화면만 비어 보일 수 있다. 소개서 캡처는 이미 로컬 파일로 떠 두었으므로 소개서 자체에는 영향이 없다.

### F-2. 데모 고지 문구가 「정적 데모」라고 말하지는 않는다

화면 문구는 「지금 보이는 멘트는 미리 적어 둔 예문이에요」다. **취지는 §4 고지와 같지만**, 화면 어디에도 「공모전용 정적 데모라서」·「API 키를 노출하지 않기 위해」라는 사유는 없다. §5 게시글 본문이 그 사유를 적으므로 게시글과 함께 읽으면 메워지지만, 화면만 보는 사람에게는 이유가 보이지 않는다. §4 의 「이 차이를 숨기지 않고 화면에서 안내한다」를 문자 그대로 만족시키려면 한 줄이 더 필요하다.

### F-3. 데모의 기본 날짜는 「빌드한 날의 다음 날」로 굳는다

정적 export 라 요청 시점이 없어서 생기는 알려진 한계다(저장소가 `deploy/README.md` 에 적어 두었다). 이번 빌드 기준 기본값은 **8월 20일**로 섰다. 사용자가 직접 고치는 길은 열려 있다. 제출 직전에 다시 빌드하면 자연스러운 날짜가 된다.

### F-5. PAGE 5 의 수치는 대조 대상이 아니다

§5 PAGE5 의 「초기 검증 지표」(추천 완료율 60% 등)는 **목표 가설**이라고 표에 스스로 적어 두었고, 「사업 모델」 5단계도 계획이다. 저장소에 대응하는 실측값이 없으므로 「어긋남」이 성립하지 않는다. 다만 소개서에서 이 표를 옮길 때 **「목표 가설」이라는 열 제목을 지우지 말 것** — 지우면 실적으로 읽힌다.
