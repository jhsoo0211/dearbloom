## 1. P0 — 고장·거짓말·접근성 차단

### P0-1. 비밀 편지: 받는 사람에게 "번호만 알면 열 수 있다"고 말하지만, 그 사람 기기에서는 **영원히 열리지 않는다**

`store.ts` 가 스스로 "이 기능의 유일한 금지선"이라 부른 것을 화면이 어기고 있다.

**파일:줄 (2026-08-17 08:5x 시점 원문)**

`src/components/letter/LetterEntrance.tsx:161`
```
받으신 편지 번호를 적어 주세요. 번호를 아는 분만 그 편지를 열 수 있어요.
```

`src/components/letter/LetterEntrance.tsx:327-329` — 기기 저장 고지
```jsx
            <p className={styles.empty}>
              편지는 지금 <b>이 기기에만</b> 남아 있어요. 브라우저 저장소를 비우면 함께 사라져요.
            </p>
```

`src/components/letter/LetterEntrance.tsx:33`
```js
const NOT_FOUND = '이 번호로 잠긴 편지를 찾지 못했어요. 한 글자씩 다시 봐 주시겠어요?';
```

`src/lib/letters/store.ts:8-10` — 파일 스스로 정한 금지선
```
 *   · 시크릿 창·저장 차단 환경에서는 아예 저장되지 않는다 —
 *     그때는 조용히 넘어가지 않고 `LetterStorageUnavailableError` 로 화면에 말한다.
 * 화면 문구가 이 사실을 숨기지 않는 것이 이 기능의 유일한 금지선이다
```

**무엇이 문제인가 (확인함)**

327-329줄의 고지는 `mine.length > 0` 분기 **안에만** 있다. 편지를 하나도 만든 적 없는 사람 — 즉 **번호를 받아서 찾아온 수신자** — 에게는 `: loaded ?` 분기의 `아직 만든 편지가 없어요.` 만 뜨고, "이 기기에만" 이라는 말은 화면에 **한 번도 나오지 않는다.**

수신자가 실제로 보는 화면 전문(Playwright `innerText` 실측, 390×844):
```
편지 열기 / OPEN
받으신 편지 번호를 적어 주세요. 번호를 아는 분만 그 편지를 열 수 있어요.
편지 번호 / 열기
...
아직 만든 편지가 없어요. 처음 한 통을 쓰면 여기에 목록이 생겨요.
```

그리고 번호를 넣으면(3종 실측 — `abc`·`!!!!!!`·`AAAA` 전부 동일):
```
이 번호로 잠긴 편지를 찾지 못했어요. 한 글자씩 다시 봐 주시겠어요?
```

편지는 **만든 사람의 브라우저 localStorage 에만** 있다(`LETTER_STORAGE_KEY = 'dearbloom.letters.v1'`). 수신자 기기에는 애초에 사본이 없으므로 어떤 번호도 맞을 수 없다. 그런데 화면은 ⑴ 번호가 열쇠라고 말하고 ⑵ 실패하면 **오타를 의심하라**고 안내하며 ⑶ `MISS_LIMIT = 5` 회 후 `WAIT_SECONDS = 20` 초 잠금까지 건다(`LetterEntrance.tsx:29-31`). 사용자를 없는 문 앞에서 다섯 번 두드리게 한 뒤 벌을 준다.

**증거**: `audit-0817/letter-open.png` · 위 `innerText` 덤프 · `store.ts:347-359`(`findByCode` 가 형식 오류·저장소 미가용을 모두 `null` 로 접는다)

**권장 처방**
- 기기 저장 고지를 `mine.length` 조건 **밖**으로 꺼내 `편지 열기` 폼 바로 옆에 세운다. 161줄을 "지금은 편지를 만든 그 기기·그 브라우저에서만 열 수 있어요" 로 고쳐 번호가 유일한 열쇠라는 인상을 없앤다.
- `resolveBrowserStorage()` 가 `null` 일 때(시크릿 창 등)는 `findByCode` 가 못 찾음이 아니라 `LetterStorageUnavailableError` 를 올려 `store.ts` 가 약속한 문장을 그대로 보여 준다.
- 20초 잠금은 **형식이 올바른 번호가 연속 실패했을 때만** 건다.

**예상 위험**: 낮음. 문구와 분기 위치 변경이 대부분이고 저장 로직은 그대로다. Supabase 어댑터로 갈아끼우면 이 문구는 다시 바꿔야 하므로, 한 상수로 뽑아 두면 그날 한 줄만 고친다.

## 2. P1 — 사용성·정확성

### P1-1. `fitScore` 는 구조적으로 **85점을 넘을 수 없다** (가중치 15%가 죽어 있다)

`src/lib/engine/weights.ts:9-16`
```ts
export const DEFAULT_WEIGHTS: Weights = {
  I: 0.3, R: 0.25, S: 0.15, A: 0.15, P: 0.1, D: 0.05,
};
```
`weights.ts:21-36` 의 `weightsSchema` 는 **합이 1.0(±0.01)** 이어야 통과시킨다. 그런데 `src/lib/engine/score.ts:161`
```ts
const total = round4(w.I * I + w.R * R + w.S * S + w.A * A + w.P * P);
```
- `D`(0.05)는 합산식에 아예 없다. 주석은 "diversity 단계에서 반영한다"고 하지만 `diversity.ts:15-31` 의 `diversify()` 는 가중치를 **인자로 받지도 않는다** — 어디서도 쓰이지 않는다.
- `P`(0.10)는 `score.ts:159` 에서 `const P = 0;` 고정 스텁이다.

따라서 실제 도달 가능한 최대는 `0.3+0.25+0.15+0.15 = 0.85`.

**확인함** — 실데이터 전수 실행(`intent: confession`·`relationship: lover`·`dateISO: 2026-08-17`·색·페르소나·향 모두 입력한 최대 조건):
```
풀 입력 → rose-red(79) lily-asiatic(53) tulip-white(35)
```
최상 조건에서도 79. 반대로 `intent/relationship` 이 모두 `other` 이고 날짜·예산이 없으면 **세 건 모두 8점**이 된다(`S=0.5` 하나만 살아 `0.15×0.5=0.075`).

**지금 화면에 노출되지는 않는다(확인함)** — 결과 화면 `innerText` 에 백분율 표기 없음. 그래서 P0가 아니다. 다만 ⑴ 값이 `build-result.ts:435` → `flow/types.ts:235` 로 화면 계층까지 이미 흘러가 있고 ⑵ `weightsSchema` 가 "합 1.0"을 강제하므로 나중에 config 로 가중치를 조정하는 사람은 자기가 준 배분과 실제 정규화가 다르다는 것을 알 수 없다.

**권장 처방**: 둘 중 하나로 정직하게 만든다 — (a) `D`·`P` 를 스키마에서 빼고 합을 4항 1.0으로 재배분하거나, (b) 합산식을 `실제 사용한 가중치 합`으로 나눠 0~1로 정규화한다. 어느 쪽이든 `fitScore` 를 화면에 올리기 전에 결정해야 한다.

**예상 위험**: 중간. 순위 자체는 단조라 바뀌지 않지만 절대값이 변하므로 `tests/engine/*` 의 기대값 스냅샷이 함께 움직인다.

### P1-2. 오늘의 꽃 366일 배정이 **26:1 로 쏠린다**

365일(2026년) 전수 실행 결과 (확인함):
```
366일 배정 종수: 47 / 카탈로그 47종  (미출현 0종)
최다: chrysanthemum=26 carnation=24 pansy=21 camellia=16 anemone=15
최소: delphinium=2 gladiolus=2 cherry-blossom=1 forget-me-not=1 aster=1
```
국화는 한 해 26일 나오고 벚꽃·물망초·과꽃은 **1일**만 나온다. 원인은 버그가 아니라 구조다 — `today.ts:134-150` 의 `candidatesFor` 가 그 달 개화월 후보만 추리는데, 개화월이 넓은 꽃은 많은 달의 후보군에 들어가고 좁은 꽃은 한 달에만 들어간다. HRW 해시(`rankByHash`)는 후보군 **안에서** 균등할 뿐 연간 노출을 고르게 하지 않는다.

부수 확인: **결정성 OK**(같은 날짜 2회 호출 365/365 동일), **연속 반복 0건**, **제철 우선 규칙 위반 0건**. 이 셋은 설계대로 돈다.

**권장 처방**: 연간 노출 상한/하한을 두려면 HRW 가중치에 "그 꽃이 후보로 등장하는 달 수"의 역수를 곱하는 방법이 가장 작다(꽃 추가·삭제 안정성은 유지된다). 다만 이것은 **의도된 동작일 수 있다** — 제철 꽃을 자주 보여 주는 것이 목적이라면 고칠 것이 없다. 판단이 필요하다.

### P1-3. 리드 문구 12벌 중 **8벌이 366일 내내 죽어 있다**

`landing-build.ts:255-293` 의 `OPENINGS` 는 `in_season`·`adjacent`·`all` 세 갈래 × 4벌 = 12벌인데, 365일 전수 실행에서 basis 분포는:
```
basis 분포: in_season=365
```
`adjacent`·`all` 갈래 8벌은 현 47종 카탈로그로는 **한 번도 화면에 오르지 않는다**(확인함). 47종의 개화월이 12개월을 모두 덮기 때문이다.

같은 이유로 `MEANING_LINES`(3벌)·`BARE_LINES`(3벌)도 뜨지 않는다 — 이쪽은 `landing-build.ts:311-312` 주석이 이미 "366일 전부 인용이 서서 화면에 오르지 않는 사다리"라고 스스로 밝혀 두었다(정직함). `OPENINGS` 의 `adjacent`/`all` 에는 그 주석이 없다.

실제로 도는 4벌의 분포는 매우 고르다(확인함): 93 / 92 / 90 / 90 (이상 91.25). `HOOK_CLOSINGS` 도 93/92/90/90, `ASIDE_LINES` 는 183/182. **쏠림 없음.**

**권장 처방**: 고칠 것은 없고 주석만 맞추면 된다 — `adjacent`/`all` 블록에도 "현 카탈로그에서는 서지 않는 사다리"라고 적어 두면 다음 사람이 그 문장을 다듬느라 시간을 쓰지 않는다.

### P1-4. 탄생화 사전 — 사진 92일(25%)·이야기 118일(32%) 미확보

365일 전수 조회(확인함):
```
탄생화 커버리지: 꽃 없는 날 0 / 사진 없는 날 92 / 이야기 없는 날 118  (총 365일)
탄생화 종수: 303
```
**꽃 이름·꽃말은 366일 빈틈이 없다.** 빠진 것은 사진과 이야기다.

표기는 정직하다(확인함) — `/flowers` 본문: `도감에 들어온 꽃은 사진과 함께 상세로 이어지고, 아직 들이지 못한 꽃은 이름과 꽃말부터 먼저 건네요.` 그리고 `birth-dict.ts:72-74` 주석대로 미확보 날은 다른 꽃 사진을 끌어다 쓰지 않고 점선 빈 액자를 세운다.

**월 목록 본문 누출은 없다(확인함)** — `buildBirthMonth`(`birth-dict.ts:206-218`) → `toEntry`(`:64-107`) 가 내보내는 필드는 `day·dateLabel·nameKo·nameEn·scientificName·meaning·meaningCopula·alsoOn·link·thumbSrc·sourceUrl·sourceLabel` 뿐이고 이야기 본문은 없다. 본문은 `loadBirthDictDetail` 로 따로 간다. 경계가 지켜지고 있다.

**권장 처방**: 콘텐츠 확충 작업이므로 코드 수정 아님. 4분의 1이 빈 액자라는 사실을 로드맵에 숫자로 남길 것.

## 5. 스킬 권고와 우리 스펙의 충돌

`ui-ux-pro-max` ux 도메인이 올린 권고 중 **우리 스펙이 이기는** 항목:

| 스킬 권고 | 우리 스펙 | 채택 |
|---|---|---|
| Typography: 본문 최소 16px, `text < 12px` 안티패턴 | §1.6 본문 최소 **14px**, §1.6b 마이크로 타이포 **12px** 하한 | **우리 스펙**. 실측 결과 12px 미만 0건이라 두 기준 모두 만족하므로 실질 충돌 없음 |
| Navigation: `html { scroll-behavior: smooth }` 를 High 심각도로 요구 | §1.6b·§1.6c 는 reduced-motion 시 즉시 전환을 요구 | **우리 스펙**. 전역 smooth 는 모션을 끈 사용자에게 강제 스크롤 애니메이션이 된다. 넣는다면 `@media (prefers-reduced-motion: no-preference)` 안에만 |
| Touch: 최소 44×44 | §1.6 동일 (44×44) | 일치 |
| Accessibility: 대비 4.5:1 | §1.6 동일, §1.5g 는 사진 위에서 **픽셀 실측**까지 요구(더 엄격) | **우리 스펙이 더 엄격** — 그 기준으로 측정했고 통과 |

- Lighthouse CLS 수치 — `layout-shift` PerformanceObserver 를 붙이지 않았다. 폰트 `swap` 과 가로 스크롤 0은 확인했으나 **CLS 실측값은 없음(의심됨 아님, 미측정)**

## 7. 우선순위 제안

1. **P0-1 비밀 편지 고지·오류 문구** — 유일한 P0이고, 사용자를 없는 문 앞에 세운 뒤 20초 벌까지 준다. 문구·분기 위치 변경이 대부분이라 위험 대비 효과가 가장 크다.
2. **P1-1 `fitScore` 85점 상한** — 지금은 화면에 안 나오지만 값이 이미 화면 계층까지 흘러가 있다. 결과 화면에 적합도를 올리기로 결정하는 순간 사고가 되므로, 올리기 전에 정한다.
3. **P1-2 오늘의 꽃 26:1 쏠림** — 고칠지 말지부터가 판단이다. "제철을 자주 보여 준다"가 의도면 문서에 적고 닫으면 되고, 아니면 HRW 가중치에 등장 달 수 역수를 곱하는 작은 수정으로 해결된다.
