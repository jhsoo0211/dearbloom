# dearbloom 디자인 시안 스펙 (3방향 × 3화면)

worker 3명이 각각 1방향(3개 HTML)을 독립 제작한다. §1 공통 스펙은 세 방향 모두 동일하게 준수하고, 목 데이터·카피는 §1.5 전문을 글자 그대로 사용한다(디자인만 다르고 콘텐츠는 동일해야 비교 가능).

---

## 1. 공통 스펙

### 1.1 산출물 파일 구조

```
design\
├── index.html                  ← 비교 페이지 (3방향 완료 후 Advisor가 제작)
├── a-botanical\  home.html / question.html / result.html
├── b-guide\      home.html / question.html / result.html
└── c-gallery\    home.html / question.html / result.html
```

- worker A → `a-botanical\` 3파일만, worker B → `b-guide\` 3파일만, worker C → `c-gallery\` 3파일만 생성. 다른 폴더는 절대 건드리지 않는다.
- 모든 파일: `<!DOCTYPE html>`, `<html lang="ko">`, `<meta charset="UTF-8">`, viewport 메타, `<title>dearbloom — {화면명} ({방향명})</title>`. UTF-8(BOM 없음) 저장.
- 화면 간 내비게이션(상대 경로): home CTA → `question.html`, question "다음" → `result.html`, 상단 로고 → `home.html`.

### 1.2 기술 규칙

| 항목 | 확정 | 이유 |
|---|---|---|
| CSS | `<style>` 인라인, 순수 CSS만. **Tailwind CDN 금지** | Tailwind Play CDN은 JS 런타임 — 오프라인이면 스타일 전멸 |
| CSS 변수 | `:root`에 §1.4 팔레트를 `--ivory --ink --stem --rose --lavender --gold`로 선언 후 사용 | hex 일탈 탐지 용이 |
| JS | 인라인 바닐라, 파일당 50줄 이내. 용도: 결과 3안 탭/전환, 멘트 3톤 탭, 복사 버튼(`navigator.clipboard.writeText` try/catch, 실패 시 무시) | 시연용 최소 |

- 자리: 챕터 01 리드 → 탄생화 각주 **아래**. 위계는 각주와 같은 단이다 — 이 줄은 읽는 것이 아니라 만지는 것이라, 리드보다 커지면 챕터의 주인공이 "오늘의 꽃"에서 색 고르기로 넘어간다
- 규격: §1.6b 칩(h44 · 선택은 `--cta-bg`/`--cta-fg` 짝 채움 **하나로만**). 머리말 `화면의 빛깔`은 11px 오버라인, 640px 아래에서는 칩 줄 위로 올린다
- **계열 색 점은 안 눌린 칩에만 있다** — 점은 그 계열이 어떤 색인지 보여 주는 **견본**이고(`숲빛`이 어떤 초록인지는 글자로 알 수 없다), 견본이 필요한 것은 아직 안 고른 쪽이다. 값은 팔레트 원색 고정(`--stem`/`--ivory-3`/`--gold`/`--rose`/`--lavender`) — 테마 변수를 쓰면 다섯 점이 전부 같은 색이 되어 견본 노릇을 못 한다. 점의 링은 `currentColor`: 고정 헤어라인(`--hair-2`)으로 두르니 계열색이 배경에 붙는 자리에서 점이 통째로 사라졌다(다크 위 숲 1.6:1 · 와인 2.49:1 — §1.6 비텍스트 하한 3:1 미달)
- **[2026-08-16 확정] 눌린 칩에는 점이 없다.** 한동안은 눌린 점을 `currentColor`로 넘겨 대비를 벌었다(원색 그대로는 채움색과 같아져 사라졌다 — 와인빛은 채움 `#8A3448`과 점 `--rose #8A3448`이 완전 일치, 금빛 1.7:1·보랏빛 2.3:1). 대비는 해결됐지만 그러면 눌린 칩이 **짝 채움 + 글자색 점** 두 가지로 선택을 말한다 — §1.6b의 "한 화면 한 선택 표현"이 금지하는 이중 표시다. 점을 지워도 잃는 것이 없다: 고른 순간 그 색은 화면 전체가 입고 있고, 견본은 남은 넷이 말해 준다
  - ⚠ 구현은 **가로 여백으로 폭을 되메운다**(`padding: 0 15px → 23.5px`, 479px 아래 `12px → 20.5px`). 점 10px + gap 7px = 17px이 빠지므로 좌우 8.5px씩을 얹어 칩의 상자를 그대로 유지한다 — 안 하면 칩을 누를 때마다 그 줄의 나머지 칩이 17px씩 밀린다
- 접근성: `role="group"` + `aria-labelledby`(머리말), 선택 상태는 `aria-pressed`, 전 항목 키보드 도달(네이티브 `<button>`). `aria-label`은 `{라벨} 색감으로 보기` — 보이는 텍스트로 시작하므로 WCAG 2.5.3 유지
- 진입 시 눌린 칩 = 오늘의 꽃 카테고리(v3.3의 "진입 시 1회 결정"은 그대로다 — 바뀐 것은 **사람이 바꾸는 방법**뿐)
- **[2026-08-16 확정] 고른 빛깔은 세션이 기억한다.** 예전에는 `useState`로만 들고 있어서 도감을 한 번 다녀오면 오늘의 꽃 카테고리로 되돌아갔다 — 사람이 고른 것이 말없이 되돌려지면 그건 선택이 아니라 장식이다. `sessionStorage` **1키**(`dearbloom.tint`, 값은 테마 slug)에 담고 게이트 세션 기억과 **같은 문법**(`useSyncExternalStore` + 서버 스냅샷 `null`)으로 읽는다 → 하이드레이션 경고 0, 뒤로 가기는 처음부터 실제 값. 저장값이 있으면 **무조건 이긴다**(선택 해제라는 개념이 없다 — "오늘의 꽃 따라가기"는 저장 전의 기본값이지 되돌아갈 상태가 아니다). 탭을 닫으면 잊는다
  - ⚠ 게이트와 달리 **부트 스크립트를 두지 않는다.** 빛깔은 `<html data-flower>`를 만져야 하는데 그 노드는 layout.tsx가 소유해 React 19가 속성 불일치를 그대로 잡아낸다(게이트가 `data-db-gate`로 겪은 그 실패). 테마는 지금도 마운트 뒤 이펙트가 입히므로 첫 프레임 기준은 달라지지 않는다
- 회귀 방어: 카테고리를 늘리면서 칩 목록을 잊으면 그 계열은 영영 고를 수 없는 색감이 된다. `tests/components/landing-today-reason.test.ts` §1.4c v3.4 블록이 칩 5개 ↔ `CATEGORY_THEMES` 전수 일치를 본다

### 1.5n 오늘의 꽃 "고른 이유" — 이야기에서 끌어온 한 문장 (2026-08-16 사용자 요청)

> **§1.5e 바로 옆에 둔다.** 이 문장은 화면에서 **우리 이야기 원문을 그대로 인용하는 유일한 자리**라, §1.5e가 명언에 세운 인용 절제 원칙(화면당 1개·본문 이하 위계·원문 존중)의 연장선이다. 번호만 뒤쪽을 쓴다.

사용자: "오늘의 꽃 추천 멘트를 감동적인 이야기나 **우리가 모은 이야기 기반으로** 감성적으로. 로컬에서도 작동."

뒷문장이 설계를 결정한다 — **모델을 부르지 않는다.** 재료(이야기 317편·꽃말·제철 근거)는 이미 카탈로그에 있으므로, 서버(`landing-build.ts`)에서 **규칙 조합**으로 짓는다. 그래서 키 없이도 돌고, 같은 날 새로고침은 같은 문장이 나온다.

**재료 3단 × `basis` 3분기 = 9칸.** 앞머리는 `basis`(제철 근거)를 사람의 말로 옮긴 한 마디이고, 뒤는 재료가 정한다.

| | ① 이야기 훅 있음 *(실데이터 32종 전부)* | ② 훅 없고 꽃말만 | ③ 둘 다 없음 |
|---|---|---|---|
| `in_season` | 일 년을 기다려 지금이 한창인 꽃이에요. **“{훅}”** — 오늘은 이 이야기부터 들려드리고 싶었어요. | 〃 ‘{꽃말}’**이라는/라는** 말을 품은 꽃이라, 오늘 같은 날 꺼내고 싶었어요. | 〃 오늘을 그냥 보내기 아까워서 먼저 꺼냈어요. |
| `adjacent` | 이제 막 제철로 들어서는 꽃이에요. **“{훅}”** — 피기도 전에 이 이야기가 먼저 떠올랐어요. | 〃 ‘{꽃말}’… 말을 품은 꽃이라, 피기 전부터 먼저 건네고 싶었어요. | 〃 피기 직전의 설렘부터 먼저 건네고 싶었어요. |
| `all` | 계절을 가리지 않고 한결같이 곁에 있는 꽃이에요. **“{훅}”** — 어느 날에 꺼내도 좋을 이야기라, 오늘 먼저 꺼냈어요. | 〃 ‘{꽃말}’… 말을 품은 꽃이라, 어느 날에 꺼내도 좋았어요. | 〃 어느 날에 꺼내도 좋아서 오늘 꺼냈어요. |

- 훅이 있으면 **꽃말은 부르지 않는다** — 한 문장에 재료 둘을 겹치면 인용이 묻힌다. ②·③은 데이터가 얇아질 때를 위한 사다리다(현 카탈로그 32종은 전부 ①)
- 꽃말 뒤 조사는 받침이 가른다(`hasFinalConsonant`) — `‘맑은 마음’이라는` / `‘인내’라는`

**인용 규칙 (확정 — 재작성 금지).** 훅은 §1.5d가 합니다체 헤드라인을 허용한 자리이고 **그 무덤덤함이 그대로 매력**이다. 문장은 손대지 않는다.
- 바깥 인용은 `“ ”`, 꽃말은 `‘ ’` — 훅 원문에 `"`·`'`가 섞여 있어(377편 중 26편, 2026-08-16 배치 1 재계산) 타이포그래픽 따옴표라야 안쪽 인용과 겹치지 않는다
- **문장 끝 마침표 하나만 뗀다.** 377편 중 272편은 `.`로 끝나고 105편은 그냥 끝나, 그대로 쓰면 `“…있습니다.” —`와 `“…있습니다” —`가 날마다 번갈아 나온다. 인용 부호 안의 문장부호는 인용하는 쪽 조판의 몫이다. `?`·`!`는 떼지 않는다(조판이 아니라 화자의 어조)

**어느 이야기를 인용하나.** 후보 순서는 슬라이드 티저와 **같은 경로**(`pickStories(flowerId, 'just_because', …)`)에서 온다 — 이야기 순서 규칙을 두 벌 두지 않는다. 다른 것은 하나뿐: 티저는 늘 1순위를 쓰고, 리드는 **`날짜 + 꽃 id` 해시로 후보 중 하나를 고른다.** 장미는 이야기가 23편이라 같은 꽃이 다시 걸려도 다른 이야기가 나온다. 결정성은 그대로다(씨앗에 시각·난수가 없다).

**리드 리듬 재조정.** 인용이 길어져(훅 최장 59자) 리드를 두 줄로 가른다.
1. `.db-today-lede` (15.5px) — `{날짜}, 오늘의 꽃은 {이름}이에요.` + 고른 이유
2. `.db-today-aside` (14.5px, 한 단 흐리게) — 화면 분위기 + 카드 넘기기 안내. **읽지 않아도 되는 줄**이라는 뜻이기도 하다
3. `.db-today-birth` (14px) — 탄생화 각주(§1.5m, 불변) → 그 아래 `화면의 빛깔` 선택기(§1.4c v3.4)

**금지선.** 이 자리는 엔진의 선정 근거를 옮기는 곳이라, 방심하면 근거를 근거의 말로 적게 된다("제철 조건에 해당하는 꽃을 자동 선정했어요"). 사무 어휘 목록(`선정·기준·조건·해당·알고리즘·데이터·자동·무작위·추출·적용·분석·엔진·로직…`)은 `tests/components/landing-today-reason.test.ts`가 지킨다 — **인용 부호 안쪽은 검사에서 뺀다**(훅은 편집자의 말이지 우리 말이 아니다. 실제로 `기준`이 든 훅이 2편 있다).

### 1.5f 이야기 수집 원칙 (2026-08-14 사용자 7차 확정)

- **문화권 무제한**: 서양·동양 가리지 않는다 — 그리스·로마, 오스만·페르시아, 중국·일본·한국, 이집트, 북유럽, 켈트 등 다양성 자체가 가치. 같은 꽃의 문화권별 상반 해석은 적극 수집
- **재미 우선**: 도파민·로맨틱·비극·유쾌 — confidence 라벨("드물게 전해지는 이야기예요")만 정직하면 출처 약한 설화도 수집 대상
- **픽션 허용**: `story_type` 구분을 도입한다 — `folklore(설화·전승) | history(역사) | literary(문학 유래) | original(dearbloom 창작)`. **original은 화면에 "dearbloom이 지어 본 이야기예요" 라벨 필수**(창작을 사실처럼 보이게 하지 않는 것이 유일한 금지선). 창작 이야기는 source_url 면제, 나머지는 출처 필수
- 실존 인물·실존 브랜드를 소재로 한 창작 금지(명예·권리). 신화 인물·역사 인물의 기록된 일화는 가능
- 적용: stories 스키마에 `story_type` 컬럼(차기 데이터 적재 작업에서 추가), 화면 라벨은 §1.5d 이야기 톤

### 1.5g 사진 위 꽃 이름 가독성 규칙 (2026-08-15 사용자 피드백 — "글씨는 보이되 감성은 살려라")

꽃 이름·꽃말이 사진 위에서 잘 안 보인다는 피드백. 전면 오버레이로 사진을 죽이지 말고 **국소 처리**로 해결한다:
- **국소 스크림**: 텍스트 블록 뒤에만 radial/linear 그라디언트 밴드(가장자리 페더 24px+) — 사진 전체 밝기는 유지
- **타이포 보강**: 꽃 이름은 마루 부리 400 이상(300 금지) + `text-shadow: 0 1px 24px rgba(base, .55)` 계열 소프트 섀도 허용(하드 아웃라인 금지)
- **배치 우선**: 가능하면 사진의 어두운 영역 위에 텍스트를 얹는 구도를 먼저 선택(이미지별 초점 좌표를 theme 상수에 기록 가능)
- **검증**: 사진 위 텍스트는 항상 픽셀 실측 4.5:1(기존 문화 유지) — 스크림·섀도 적용 후 기준
- 적용 대상: 랜딩 히어로·오늘의 꽃, 앱 홈 히어로 카드, 그룹 부케 카드 등 사진 위 모든 세리프 텍스트

**호버 강화 상태 (2026-08-15 사용자 10차 — "커서를 가져가면 잘 보이게")**
- 기본 상태는 위 규칙대로 **항상 읽히는 상태**(4.5:1) — 호버로만 보이는 텍스트 금지(모바일에 호버 없음, §1.6 앤티패턴)
- `:hover`/`:focus-visible`/터치 시 **강화 상태**: 국소 스크림 심도 증가(예: .35→.65) + 꽃 이름 밝기·크기 소폭 상승(scale ≤1.03) + 꽃말·설화 티저 1줄 추가 노출. 전환 200~300ms, reduced-motion 시 즉시
- 터치 기기: 첫 탭 = 강화 상태 토글(두 번째 탭이 링크 이동이 되지 않게 카드 전체 링크와 분리), 슬라이드 스와이프와 제스처 충돌 금지

### 1.5i 결과 화면 위계 확정 + 꽃말 조합기 로드맵 (2026-08-15 사용자 12차)

**결과 화면 정보 위계 (위 → 아래)**:
1. **꽃 (3D/사진) + 꽃 이름 + 꽃말** — 주인공, 최대 크기

3. 추천 이유 · "이런 날 건네보세요" 상황 예시
   - **이야기 내부 위계 (2026-08-15 사용자 16차)**: 카드·상세 시트 모두 **hook·본문(이야기 자체)이 먼저** — 문화권("케냐" 등)·시대·갈래·신뢰 라벨 메타는 본문 **아래** 각주 줄로 후치. 카드 상단에 지역·시대 칩 금지(꽃 이름·mood 칩만 상단 허용)

### 1.5j 에피소드·상대방 서술 입력 (2026-08-15 사용자 13차 — "스토리·감성·생각해주는 마음")

결과 화면은 이미 768/1024 에서 폰 프레임을 버렸지만 **질문 화면과 `/groups` 는 아직 앱이었다.** `/groups` 는 문자 그대로 430px 캔버스에 radius 40px + 네 겹 그림자를 둘러 화면 한가운데 띄워 두었고, 질문 화면은 캔버스는 사라졌어도 묻는 말과 고르는 칸이 한 줄로 쌓인 좁은 기둥이라 앱 위저드로 읽혔다.

- **질문 화면 (1024px↑)**: 결과와 **같은 1120px 칼럼**에 2단. 좌단(320px, sticky) = 묻는 말(오버라인·제목·리드), 우단(≈690~710px) = 답. 헤어라인 한 줄로 가른다. 고정 푸터바는 768px↑에서 이미 본문 흐름 버튼이고, 1024px↑에서는 **우단 시작점에 맞춰** 답 바로 아래에 선다(왼쪽 끝에 서면 2단이 도로 무너져 보인다). 칩·프리셋 줄은 넓어진 우단을 그대로 쓴다.
- **`/groups` (768px↑)**: 폰 캔버스·라운드·그림자 제거, 셸이 추천 플로우 `.frame` 과 같은 다크 그린 워시를 깔고, 상단바 = 사이트 헤더, 본문 = 1120px 중앙 칼럼. **1024px↑에서는 왼쪽 입력(마음·명단) / 오른쪽 결과(`.resultCol`) 2단** — 이 화면은 "적고 → 눌러서 → 아래에 나온 것을 본다"가 아니라 적으면서 결과를 함께 보는 화면이고, 세로로만 쌓으면 명단이 길어질수록 결과가 화면 밖으로 밀린다. 두 섹션(결과 패널·카드에 담기)을 한 래퍼로 감싸는 이유는 단을 가르는 **헤어라인이 한 줄이어야** 하기 때문이다.
- **모바일(<768px)은 무회귀.** 두 화면 모두 새 래퍼가 그냥 블록이라 DOM 순서 = 지금까지의 한 칼럼 순서 그대로다.
- 검증: 390·768·1280·1536 에서 위저드 5걸음 + 결과, `/groups` 완주 — 가로 스크롤 0, 데스크톱에 좁은 부유 캔버스 없음, 단계 포커스(`#q-title`)·live region 무회귀.

- **입력은 월·일 셀렉트 2칸.** `<input type="date">`는 쓰지 않는다 — 연도를 반드시 끼워 받는데 탄생화에는 연도가 없고(366일 달력), 브라우저마다 위젯이 달라 §1.6b 규격(h44·1px 보더)이 화면마다 흔들린다. 셀렉트는 §1.6b pill 규격으로 그린다(h44·`appearance:none`·직접 그린 화살표·글자 16px — iOS 확대 방지).
- **일 목록은 월에 따라 줄어든다.** 2월은 **29일까지**(2월 29일도 실재하는 생일이다). 달력 값은 상수를 베끼지 않고 **표에서 센다**(`birthCalendar`).
- **결과 한 장**: 날짜 · 이름 · 영문명/학명(있을 때) · 꽃말 · 도감 링크 또는 미매칭 문구 · 계보 각주.
  - 매칭: 보조 버튼(pill h44) `도감에서 {도감 이름} 보기`. 표 이름과 도감 이름이 다를 수 있어(`노랑수선화`↔`수선화`) **도착지 이름을 함께** 보여 준다.
  - 미매칭(309일): `도감에는 아직 없는 꽃이에요 — 이름과 꽃말만 먼저 건네요.`
  - 각주: ①의 문장 그대로. **결과 카드마다 붙는다.**
- **결과 자리는 비어 있어도 높이를 갖는다**(`min-height`). "찾는 중" → 카드 전환에 아래 CTA가 밀리면 그것이 곧 레이아웃 이동이다(CLS 0 규율).
- **데이터 경로: 서버 액션**(`app/flowers/actions.ts`). 366행을 클라이언트에 내려보내면 첫 응답이 50~60KB 무거워지는데 실제로 읽히는 것은 **하루치 한 장**이다 — `/stories`가 이야기 317편 전문으로 겪은 문제와 같은 모양이라 같은 답을 쓴다(성능 리뷰 P1-7). 미리 내려보내는 것은 일 셀렉트가 쓸 **달력 12개 숫자**뿐이다.

**④ 도감 상세 `/flowers/[slug]` — 놓인 날 한 줄**

`참고` 블록(⑤ 반려동물·계절·가격) **아래**에 한 줄. 카드 격자에 넣지 않는 이유는 이것이 그 꽃의 성질이 아니라 **날짜 표가 그 꽃을 어디에 놓았는가**이기 때문이다 — 같은 격자에 넣으면 도감이 확인해 준 사실처럼 읽힌다.

> `이 꽃이 탄생화로 놓인 날 — 3월 21일 · 10월 9일`  `널리 통하는 탄생화 표에서 가져왔어요.`

- 한 종이 **여러 날**에 걸리는 것이 정상이다(장미 10일 · 국화 4일). 달력 순으로 잇는다.
- 표에 안 걸린 꽃(47종 중 9종 — 2026-08-16 배치 1 반영)은 **줄 자체를 세우지 않는다**(빈 각주를 남기지 않는다).

**⑤ 2단 티어 — 정식 도감과 탄생화 사전 (2026-08-16 사용자: "탄생화를 가져왔으면 꽃이 365개 이상이어야 하는 거 아니야?")**

맞는 지적이다. 탄생화는 366일이고 그 표가 부르는 이름은 **303가지**인데, 도감에 실린 꽃은 32종뿐이었다. 두 숫자가 한 화면에 있으면서 설명이 없으면 도감이 뭔가를 숨기는 것처럼 읽힌다. 그렇다고 303가지를 전부 "도감의 꽃"으로 올릴 수는 없다 — 정식 도감 한 종에는 색깔별 꽃말(출처 포함)·이야기·반려동물 안전성·실사·도판이 붙어 있고, 표에서 온 이름에는 **이름과 꽃말 한 줄**밖에 없다. 그래서 합치지 않고 **층을 나눈다.**

| | **정식 도감** (47종 — 2026-08-16 배치 1로 32→47) | **탄생화 사전** (366일 · 미보유 이름들) |
|---|---|---|
| 근거 | `content/flowers.csv` + meanings·stories·pet_safety | `content/birth_flowers.csv` 한 표 |
| 갖는 것 | 색깔별 꽃말(출처별)·이야기·안전성·실사·도판·상황 | 이름 · 영문명/학명(있는 날만) · 꽃말 한 줄 · 놓인 날 · 출처 |
| 열람 | `/flowers/[slug]` **상세 페이지** | 사전 **시트**(라이트) — 페이지를 만들지 않는다 |
| 화면 표시 | 목록 줄 오른쪽 `도감`(액센트) + 실사 썸네일 | 목록 줄 오른쪽 `사전`(흐림) + **빈 액자** |
| 검증 | 반려동물 안전성까지 확인 | **미확인** — 그 사실을 시트가 말한다 |

- **왜 사전 항목에 상세 페이지를 주지 않나**: 여섯 줄로 `/flowers/[slug]` 같은 한 장을 세우면 정식 도감과 **같은 무게로 읽힌다**. 사진도 이야기도 안전성도 없는 페이지가 도감 상세인 척하게 된다.
- **티어 고지 두 줄**(사전 시트, §1.5d 톤). 원본은 `src/components/flowers/birth-copy.ts` — 화면마다 새로 짓지 않는다.
  > `아직 도감에 들이지 못한 꽃이에요 — 이름과 꽃말부터 먼저 건네요.`
  > `색깔별 꽃말과 이야기, 반려동물 안전성은 아직 확인하지 못했어요.`
  둘째 줄이 이 블록의 존재 이유다. **반려동물 안전성은 §1.5h 가 직설을 요구하는 항목**이고, 확인하지 않은 것을 말하지 않으면 사전 항목이 "안전한 꽃"으로 오해된다. 이 블록만 면(배경+보더)을 갖는 이유도 그것이다 — 건너뛰어 읽히면 안 된다.
- **사진을 지어내지 않는다.** 매칭되지 않은 줄은 **빈 액자**(점선 44×44)로 남긴다. 아이콘·색면·다른 꽃 사진으로 채우면 두 티어가 같은 무게로 보인다.
- **인트로 통계도 두 층으로 말한다**: `47 종 · 정식 도감` / `366 일 · 탄생화 사전` / 꽃말 / 이야기. 인트로에서 두 층을 말하는 것은 **이 라벨까지**다.
- ⚠ **차이를 설명하는 문단은 인트로가 아니라 사전 구획 안에 둔다**(`.dictTierNote` — 면 없음, 랜딩 각주와 같은 판단). 인트로는 `<main>` **위**라, 웹폰트가 늦게 도착한 로드에서 그 문단의 줄 수가 바뀌면 아래 화면 전체가 밀린다 — 2026-08-16 실측으로 1280px CLS 가 **0.005 → 0.17** 로 뛰었고(6회 중 재현), 문단을 사전 구획으로 옮기자 0 으로 돌아왔다. 첫 화면 밖에서 일어나는 재배치는 이동으로 세어지지 않는다. **인트로에 설명 문단을 덧붙이지 마라.**
- 그 문단의 **마지막 문장이 ①의 워딩 대전제**다(`BIRTH_SOURCE_NOTE` 를 그대로 이어 붙인다).

*⑤-2 열람 화면 — 도감 `/flowers` 사전 구획*

생일 꽃 찾기 **아래**, 하단 CTA **위**. 이름 검색이 "아는 꽃", 생일 찾기가 "내 날짜 하루"라면 여기는 **표 전체를 훑는** 문이다.

- **달 칩 12개**(§1.6b 칩 규격 — pill h44 고정, 선택은 `--ctrl-on` 짝 채움 **하나로만**). 390px 에서 세 줄로 접힌다.
- **처음에는 아무 달도 펼치지 않는다.** 자동으로 한 달을 열면 `/flowers` 를 여는 모든 사람이 쓰지도 않을 9KB 남짓과 썸네일 대여섯 장을 받는다. **그 한 번의 클릭이 페이로드의 문지기다.** (`new Date()` 로 이번 달을 정하면 SSR·CSR 이 갈리는 문제도 따라온다.)
- **목록은 하루 한 줄**: 일 · 썸네일(또는 빈 액자) · 이름/꽃말 · 티어 표시. 검색 결과(`.results`)와 **같은 분기**로 접는다(720px 2단 / 1040px 3단) — 31줄을 한 칼럼에 세우면 2,000px 이 넘고, 한 화면에서 목록이 두 가지 방식으로 접히면 그것부터 읽힌다.
- **매칭 줄은 `<a>`, 미매칭 줄은 `<button>`.** 겉모습을 같게 두고 클릭 동작만 바꾸면 화면 낭독기에서 둘이 구별되지 않는다 — 하나는 "링크", 하나는 "버튼"으로 들려야 어디로 가는지 알 수 있다.
- **사전 시트**(라이트 상세): 날짜 · 이름 · 영문명/학명 · 꽃말 · **표에서 이 이름이 놓인 다른 날** · 티어 고지 두 줄 · 표 출처 링크 · 계보 각주. 규격은 `/stories` `StorySheet` 그대로(모바일 바텀 시트 → 768px↑ 가운데 카드, `aria-modal`·포커스 트랩·ESC·배경 탭·body 스크롤 잠금).
  - `StorySheet` 와 달리 **열 때 다시 가져오지 않는다.** 사전 한 줄이 통째로 200바이트 남짓이라 이미 받은 달치 목록 안에 시트가 쓸 것이 전부 있다.
  - `표에서 이 이름이 놓인 다른 날` 은 **이름**으로 역조회한다(`birthDaysOfName`). 309일에는 `flowerId` 가 없어 이름이 유일한 신원이기 때문이다. ⚠ 도감 상세(④)는 계속 `birthDaysOf`(flowerId)를 쓴다 — 그쪽의 신원은 카탈로그의 꽃이고 표 이름과 다를 수 있다(`노랑수선화` ↔ `수선화`). 두 함수를 바꿔 쓰지 마라.
- **데이터 경로: 서버 액션 `listBirthMonth(month)`** — 자르는 단위가 **한 달**이다. 366행 통짜(64.8KB / gzip 9.2KB)를 첫 응답에 얹지 않는다는 ③의 규율을 이 모양이 강제한다: 화면이 받을 수 있는 가장 큰 덩어리가 31행이다.
  - **실측**(2026-08-16, `JSON.stringify` 기준): 한 달 **8.2~10.0KB / gzip 1.4~1.8KB**(2월 8.32 · 1월 9.99). 12달을 다 눌러도 111KB / gzip 19.9KB 지만, 그렇게 훑는 사람은 없다 — 사람이 여는 것은 자기 달과 선물할 사람의 달이다.
  - 한 줄이 출처 URL(70B)을 그대로 들고 있어 raw 의 약 1/4 이 같은 문자열의 반복이다. **인덱스로 접지 않았다** — 전송은 압축돼 나가므로 그 반복이 실제로 무는 값은 gzip 기준 0.2KB 남짓인데, 병렬 배열과 첨자는 읽는 사람이 매번 되짚어야 하는 비용이다. 압축이 지우는 중복을 코드로 지우지 마라.
- ⚠ **액션을 늘리면 정적 데모 쌍둥이도 늘려라** — `src/lib/demo/flowers-actions.ts`. `NEXT_PUBLIC_STATIC_DEMO=1` 빌드는 `@/app/flowers/actions` 를 **통째로** 그 파일로 갈아 끼우므로(turbopack `resolveAlias`), 앱에만 있는 export 는 데모에서 `undefined` 가 되고 `npm run build:static` 이 깨진다. 값은 브라우저에서 다시 조립하지 말고 빌드 타임에 **서버와 같은 함수**(`buildBirthMonth`)로 굳힌다(`scripts/build-demo-catalog.mjs` → `data/birth-months.ts`).

**⑥ 승격 파이프라인 — 사전에서 정식 도감으로**

2단 티어는 **영구 분리가 아니라 대기열**이다. 사전 303가지 이름은 "싣지 않기로 한 꽃"이 아니라 "아직 검증하지 못한 꽃"이고, 주간 콘텐츠 루틴(`.github/` 워크플로 · `docs/` 콘텐츠 운영)이 그중 몇 종씩 정식 도감으로 올린다.

한 항목이 정식 도감으로 올라오려면 **네 가지가 다 있어야 한다** — 하나라도 비면 승격하지 않고 사전에 그대로 둔다(반쪽짜리 도감 항목을 만들지 않는다):

1. `flowers.csv` 한 행 — 학명·색·개화월·향·가격대까지. **학명이 종을 특정해야 한다**(표의 이름만으로 종이 갈리는 경우가 있다 — 조사 문서 §8).
2. `meanings.csv` 최소 한 행 — **출처 URL 필수.** 출처 없는 꽃말은 싣지 않는다(§1.5).
3. `pet_safety.csv` — 개·고양이 두 종 전부. **여기가 승격의 병목이다.** 안전성을 확인하지 못한 꽃은 도감에 올리지 않는다(§1.5h).
4. 실사 한 장(`src/lib/photos`) — 승인 소스(Unsplash·Pexels)에서, **종이 동정되는 컷**으로.

승격하면 화면은 **저절로** 따라온다. `birth_flowers.csv` 의 `flower_id` 한 칸을 채우는 순간:
- 사전 목록 줄이 `사전`(빈 액자) → `도감`(썸네일 + 상세 링크)으로 바뀌고,
- 생일 꽃 찾기 결과 카드에 `도감에서 … 보기` 버튼이 서고,
- 도감 상세에 `이 꽃이 탄생화로 놓인 날` 줄이 생기고(④),
- 인트로 통계의 `정식 도감 N종` 이 하나 올라간다.

즉 **승격 작업은 CSV 편집이고 화면 코드는 손대지 않는다.** 숫자를 상수로 베껴 두지 않고 전부 표에서 세는 이유가 이것이다(`birthSpeciesCount`·`birthCalendar`·`flowers.length`).

**⑦ 로드맵 — 아직 하지 않은 것**

- `editorial_note`(158행)는 **화면 비노출**이다. 종 차이처럼 사용자에게 알려야 하는 사실을 내보내려면 `quotes.caveat` 같은 별도 컬럼이 필요하다 — 지금은 없다(조사 문서 §8-4).
- 월 단위 탄생화(영국식·미국식)는 싣지 않았다. 날짜별 표와 출전이 다른 계보라 섞으면 둘 다 흐려진다.
- 사전에는 **검색이 없다**(달로만 훑는다). 303가지 이름을 이름으로 찾게 하려면 색인을 클라이언트로 내려보내야 하는데, 그것이 곧 ③이 막아 둔 "366행 통짜"다. 필요해지면 검색도 서버 액션으로 간다.
- 사전 시트에는 **이전/다음이 없다.** 한 항목이 여섯 줄이라 넘겨 볼 이유가 크지 않고, 넘기려면 목록으로 돌아가는 편이 자기 날짜를 찾는 동선에 맞다.

### 1.6 접근성·품질 공통 규칙

- 본문 대비 4.5:1↑, 최소 폰트 14px, 터치 타깃 44×44px↑.
- SVG 비주얼: `role="img"`+`aria-label`(예: "흰 튤립 일러스트"), 장식용 `aria-hidden="true"`.
- 탭: `role="tablist"/"tab"/"tabpanel"`, `aria-selected`, `<button>` 사용.
- 진행 표시 `aria-label="5문항 중 1번째"`. 헤딩 h1→h2→h3 순차.

### 1.7 꽃 비주얼(SVG)

분홍 장미·흰 튤립·푸른 히아신스를 인라인 SVG로 단순화해 직접 그린다. 사실적일 필요 없음 — 방향별 스타일에 맞는 추상화. viewBox 정사각(0 0 200 200) 권장, 색은 팔레트·파생 틴트만.
