## 1. 한 문장 정의와 본질

> **꽃말과 그 꽃에 얽힌 이야기로, 지금 이 상황에 건넬 한 송이를 골라 주는 서비스.**

v1은 이 서비스를 "꽃·꽃말·함께 줄 선물·멘트를 한 번에 주는 **관계형 선물 컨시어지**"로 정의했다. 착수 세션에서 사용자가 본질을 다시 좁혔다.

**메인은 꽃말과, 그 꽃말에 얽힌 다양한 이야기다.** 지금 상황에 맞는 이야기를 먼저 보여주고, 사용자가 원하면 같은 꽃의 다른 이야기를 계속 탐색할 수 있게 한다. 꽃말 자체도 하나로 확정하지 않는다 — 문화권별·색상별로 갈라지는 여러 갈래를 모두 수집해서 보여주는 것이 서비스의 값이다.

추천·멘트·선물은 이 축을 실제로 쓸 수 있게 만드는 **수단**이지, 그 자체가 목적이 아니다. 판단이 갈릴 때는 "이야기를 더 잘 전하는 쪽"을 고른다.

### v1 대비 달라진 것

| 항목 | v1 | v2 (확정) | 근거 |
|---|---|---|---|

| 콘텐츠 축 | 꽃말 30종(출처 검수) | 꽃말(문화권·색상별 다중) + 이야기 4종 | §1.5f |
| 화면 어휘 | "출처 2곳 검수", "자료 간 차이" | 이야기 톤 — "두 갈래로 전해지는 이야기" | §1.5d |
| 무드 | Warm Ivory 라이트 + Wine Rose 중심 | **나이트 보태니컬 아카이브** — 다크 그린 베이스, Rose는 소형 포인트로 강등 | §1.4b |
| 진입 | 5문항 단일 플로우 | 모드 4종(한 명 / 여러 명 각각 / 단체 부케 / 화해의 꽃) | §1.5c, §1.5d |

| 랜딩 | 정적 히어로 1개 | **오늘의 꽃이 테마를 구동**(꽃-테마 5종 크로스페이드) | §1.4c v3.1 |

| 창작 콘텐츠 | 금지(검수 DB 밖 생성 금지) | `story_type=original` 허용, **단 라벨 필수** | §1.5f |

**바뀌지 않은 것 (후퇴 금지선)**: 사실은 DB에서, LLM은 화법만. 반려동물 안전은 LLM 추정 금지. 명언은 `quotes` 테이블 밖에서 생성 금지. 심각 상황은 생성 호출 **전에** 차단. 규칙 엔진은 순수 함수. 개인 텍스트(추억·멘트·사과문) 원문은 로그·분석 어디에도 남기지 않는다.

## 2. 핵심 사용자 경험

### 2.1 진입 모드 4종 (§1.5c, 워딩은 §1.5d)

| 모드 | 화면 카피 | 엔진 대응 |
|---|---|---|
| 한 명에게 | "마음을 전할 한 사람이 있어요" | `recommend()` — 3안 |
| 여러 명 각각 | "여러 명에게 각자 다른 꽃을 주고 싶어요" | `recommendGroupIndividual()` — 최대 10명, 꽃 중복 회피 |
| 단체 부케 | "팀·모임에 함께 줄 꽃 한 다발" | `recommendGroupBouquet()` — 최대 3종, 교집합 안전 검사 |
| 화해의 꽃 | "먼저 손 내밀고 싶은 날이에요" (Lavender 포인트) | intent=`apology` + 사과 배너·톤 제약 |

"사과·화해" → "화해의 꽃", "사과해야 해요" → "먼저 손 내밀고 싶을 때"로 바꾼 것은 §1.5d의 결정이다. 사용자는 자기 상황을 직설적으로 라벨링당하는 것을 부담스러워했다. **다만 안전 문구(반려동물·향)는 직설을 유지한다** — 여기서 완곡해지면 위험이 된다.

단체 부케의 핵심 장면은 **"지수님의 반려묘를 생각해 백합류는 부케에서 뺐어요"** 한 문장이다. 사람 여러 명의 제약을 교집합으로 걸러 낸 결과를 이유와 함께 말해 주는 것이, 이 모드가 존재하는 이유다.

### 2.2 5문항 플로우

한 화면 한 질문, 45초 목표. 어휘는 전부 엔진 `normalize.ts`에 고정되어 있다.

| # | 질문 | 값 |
|---|---|---|
| 1 | 어떤 사이인가요? | 관계 6종 — 연인·배우자·썸·친구·가족·동료 |
| 2 | 어떤 마음인가요? | 상황 7종 — 사과·고백·감사·축하·위로·기념일·그냥 |
| 3 | 상대는 어떤 분인가요? | 페르소나 태그 5종(차분한·화려한·귀여운·우아한·미니멀) + 좋아하는 색 칩 + 자유 한 줄(선택) |
| 4 | 조심할 게 있나요? | 반려동물(고양이·강아지), 향 민감, 피하고 싶은 꽃 |
| 5 | 언제, 얼마나? | 예산 구간, 전달일(계절 가용성 판정에 사용) |

3번(페르소나)이 v1에 없던 문항이다. 태그·색 선호가 점수의 A 항으로 들어가고(태그 0.6 / 색 0.4 가중 평균), 결과 화면의 "이 색으로 주세요" 추천 근거가 된다.

### 2.3 결과 화면 구성

정보 위계는 v1 원칙 그대로 **꽃·꽃말·이유가 먼저, 멘트는 그 아래**다.

| 블록 | 내용 | 원천 |
|---|---|---|
| 맥락 요약 | 입력값 한 줄 (칩 또는 오버라인) | §1.5 |
| 사과 배너 | "꽃보다 마음이 먼저예요. 아래 문장부터 건네보세요." — Lavender 필수 | §1.5d |
| 꽃 3안 | 안심 / 의미 / 대담. 꽃 이름·학명·꽃말(주인공 문장)·신뢰 라벨(이야기 톤)·추천 이유·피해야 할 경우·계절·반려동물 배지·함께 주면 좋은 것·가격대 | §1.5 |
| **색상 재선택** | "이 색으로 주세요" + 색 칩 4개. 칩을 고르면 꽃말·신뢰 라벨이 즉시 갱신. 추천 색이 아닌 색을 고르면 안내 1줄 | §1.5c |
| **꽃에 얽힌 설화** | 상황에 맞는 이야기 1편(featured) + "다른 이야기" 목록 | §1.5b, §1.5d |
| **나라별 꽃말** | 4행 미니 표 (터키·네덜란드·영국 빅토리아·한국 현대) | §1.5b |
| 멘트 3톤 | 톤 탭 전환 + 복사 버튼. 사과 상황은 유쾌 톤 제외 각주 | §1.5 |
| 명언 1개 | "함께 담을 한 줄" — 화면당 최대 1개, 본문 이하 위계 | §1.5e |
| 공유·아웃링크 | 카드에 담기 / 카카오 공유 / 이미지 저장, 제휴 2개 + 고지 | v1 §2.3 |

다른 두 안의 이야기·나라별 꽃말은 접힌 티저 1줄("이 꽃의 이야기와 나라별 꽃말 보기")로만 노출한다. 세 안을 모두 펼치면 결과 화면이 무너진다.

### 2.4 오늘의 꽃이 테마를 구동하는 랜딩 (§1.4c v3.1)

**색을 따로 고르는 게 아니라, 맨 위 꽃이 바뀌면 컨셉 컬러가 따라 바뀐다.** 컨트롤은 "꽃 칩" 하나로 통합했다 — 스와치를 누르는 행위가 곧 꽃 선택이다. 선택하면 배경·CTA·사진 틴트·오늘의 꽃(이름·꽃말·이미지)이 **세트로** 크로스페이드한다.

- 자동 로테이션 10초 + 일시정지 버튼. `prefers-reduced-motion`이면 즉시 전환(애니메이션 없음)
- 실서비스 매핑: 날짜 기반 "오늘의 꽃" 데이터가 테마를 결정한다 — 매일 다른 색의 사이트가 된다
- 구현본: `design/landing-v3/home.html` (5개 `data-theme`: tulip / lily / freesia / anemone / hellebore)

랜딩은 Deep Beauty(#10)의 **scroll room** 챕터 구조를 골격으로 삼는다. 앱은 랜딩 v3의 언어(실사·세리프·꽃-테마)를 모바일로 이식하되 기능(3D 뷰어·모드 4종·그룹·색상 재선택)을 유지한다.

## 3. 콘텐츠 전략 (v2의 핵심)

이 장이 v1에 없던 새 장이며, 본질 재정의의 실행 계획이다.

### 3.1 수집 원칙 (§1.5f)

| 원칙 | 내용 |
|---|---|
| **문화권 무제한** | 그리스·로마, 오스만·페르시아, 중국·일본·한국, 이집트, 북유럽, 켈트 — 서양·동양을 가리지 않는다. 같은 꽃의 문화권별 **상반된** 해석은 특히 적극 수집 |
| **재미 우선** | 도파민·로맨틱·비극·유쾌. confidence 라벨만 정직하면 출처가 약한 설화도 수집 대상이다 |
| **픽션 허용** | `story_type=original`(dearbloom 창작) 허용 |
| **유일한 금지선** | 창작을 사실처럼 보이게 하지 않는 것. `original`은 화면에 **"dearbloom이 지어 본 이야기예요" 라벨 필수** |
| **인물 제약** | 실존 인물·실존 브랜드를 소재로 한 창작 금지. 신화 인물·역사 인물의 **기록된** 일화는 가능 |

꽃말도 같은 원칙이다. 하나로 확정하지 않고 문화권·색상·시대별로 갈라진 채 수집해, 갈래가 나뉜다는 사실 자체를 콘텐츠로 보여준다.

### 3.2 story_type 4종과 라벨 규칙

| story_type | 뜻 | source_url | 화면 라벨 |
|---|---|---|---|
| `folklore` | 설화·전승 | 필수 | 신뢰도에 따라 §3.4 표의 이야기 톤 라벨 |
| `history` | 역사적 사실 | 필수 | 동일 |
| `literary` | 문학 유래 | 필수 | 동일 |
| `original` | dearbloom 창작 | **면제** | **"dearbloom이 지어 본 이야기예요" (필수·생략 불가)** |

`story_type` 컬럼은 아직 `content/stories.csv`와 `db/migrations/0005_story_tags.sql`에 **없다.** 다음 데이터 적재 작업에서 CSV 컬럼 + 마이그레이션 `0006` + zod 스키마를 함께 추가한다. 라벨 누락이 시드에서 걸러지도록, `original`인데 라벨 규칙을 만족하지 않으면 시드 실패로 처리한다.

### 3.3 mood·intent 태그와 선별 엔진

이야기를 많이 모아도 **상황에 맞는 한 편을 앞세우지 못하면 값이 없다.** 그래서 이야기마다 두 축의 태그를 단다.

| 태그 | 어휘 | 의미 |
|---|---|---|
| `moods` (필수, 1개 이상) | `romantic` `tragic` `funny` `mythic` `dramatic` `healing` | 이야기의 결. `moods[0]`이 대표 분위기이자 목록 다양성의 기준 |
| `intents` (선택) | 앱의 상황 어휘 7종 | 특히 어울리는 상황. **비어 있으면 "모든 상황"** 이라는 뜻이지 "미분류"가 아니다 |
| `hook` (선택) | 자유 텍스트 한 줄 | 본문 앞에 먼저 보여 줄 티저 |

선별기 `pickStories(flowerId, intent, stories, k=4)`의 규칙:

1. **1순위** — `intents`에 지금 상황이 있는 이야기를 featured로 올린다
2. **2순위** — 없으면 `MOOD_AFFINITY`로 고른다 (예: 사과 → `healing`). 단 **다른 상황용으로 명시 태그된 이야기는 결이 맞아도 건너뛴다**
3. **3순위** — 상황도 결도 안 맞으면 첫 이야기를 그대로 내보낸다 (이야기를 버리지 않는다)
4. `others`는 같은 결이 연달아 나오지 않게 재정렬한다. 전부 같은 결이어도 버리지 않는다

이 규칙 전부가 `tests/engine/stories.test.ts`에 케이스로 고정되어 있다.

### 3.4 톤·워딩 원칙 (§1.5d)

사용자 판단: "신뢰·출처 검수 같은 워딩은 별로. 정확성보다 이야기·설화 톤."

**핵심: 데이터 레이어(`source_url`·`confidence_level`)는 그대로 두고, 바꾸는 것은 화면에 보이는 문구뿐이다.** 정직성을 낮춘 것이 아니라 정직성을 말하는 방식을 바꾼 것이다.

| confidence_level | 폐기된 문구 | 확정 문구 |
|---|---|---|
| `repeated` | 여러 (현대) 자료에서 반복됨 | **오래, 두루 전해지는 꽃말** |
| `varies` | 자료 간 차이 있음 · 출처 2곳 | **시대마다 조금씩 다르게 전해져요** |
| `single_source` | 단일 자료 — 참고만 해주세요 | **드물게 전해지는 이야기예요** |
| — | 출처 2곳 검수 · 2026.08 | **두 갈래로 전해지는 이야기** |
| — | `꽃 이야기` (섹션 라벨) | **꽃에 얽힌 설화** |
| — | 출처: 브리태니커 · 위키피디아… | **이야기의 갈래 — 위키피디아 Tulip mania 외** (소형 각주) |

푸터도 개정됐다: "꽃말은 시대와 나라를 건너며 조금씩 다른 이야기가 돼요. dearbloom은 그 갈래를 함께 들려드려요."

**예외**: 안전 관련 문구(반려동물·향)와 `색상·문화권에 따라 해석이 달라요`는 그대로 유지한다.

### 3.5 명언 절제 (§1.5e)

명언은 있으면 좋지만 주인공이 아니다. 원칙은 넷이다.

- **화면당 최대 1개** — 주인공은 꽃·꽃말·멘트
- **본문보다 작거나 같은 위계**
- **검증된 인용만** — 퍼블릭 도메인 원전 확인. `quotes` 테이블(`license: pd | original`) 밖 생성은 금지
- **출처는 이야기 톤 각주로** (§1.5d)
- **질문·그룹·파트너 화면에는 넣지 않는다**

확정 목 데이터 3건: 에머슨 〈Hamatreya〉(1846, pd) — 랜딩 인용 밴드 / 김소월 〈산유화〉(1925, pd) — 앱 결과 "함께 담을 한 줄" / dearbloom 자체 문장(original) — 앱 홈 오늘의 꽃 하단.

### 3.6 콘텐츠 파이프라인

```text
① 리서치        문화권 스윕 · 꽃 1종당 3~5편 목표 · 출처 URL 기록
   ↓
② 자체 리텔링   원문 번역·복붙 금지. 우리 문장으로 다시 쓴다(저작권·톤 양쪽)
   ↓
③ 검수          story_type 판정 · confidence_level 판정 · moods/intents/hook 태깅
   ↓
④ CSV 적재      content/stories.csv (UTF-8 BOM 없음, LF, 배열은 | 구분)
   ↓
⑤ 시드 게이트   npm run seed → zod 스키마 + 3종 교차 검증. 실패하면 배포 차단
   ↓
⑥ DB            npm run seed:apply → flower_stories upsert
```

⑤의 교차 검증 3종은 이미 동작한다: **flower_id 참조 무결성**, **반려동물 안전 전수 커버리지**(꽃 × cat/dog), **공유 어휘 일치**(relationship·intent·tone·mood). 필수 필드가 비면 시드가 실패하고, 그것이 v1이 말한 "데이터 완전성 미달 시 배포 차단"의 구현체다.

현재 진행 중인 리서치는 **9종 꽃 · 설화 35편 이상**(모란 포함)이며, 완료되면 `stories.csv`가 5행에서 40행 규모로 늘어난다.

### 5.5 LLM·파인튜닝 방침 (세션 확정)

**지금은 파인튜닝하지 않는다.** 근거 셋:

1. **구조가 이미 리스크를 제거했다.** 사실(꽃말·안전·명언)은 검수 DB에서 나오고 LLM은 화법만 담당한다. 환각·독성 오류·저작권 리스크는 모델 품질이 아니라 이 경계가 막는다 — 파인튜닝으로 더 낫게 만들 대상이 없다
2. **학습 데이터가 0건이다.** 사용자가 실제로 채택한 문장이 없는 상태의 파인튜닝은 우리 톤이 아니라 우리 추측을 학습시키는 일이다
3. **대신 원료를 모은다.** `msg_copy{tone}` 채택 이벤트(어느 톤이 실제로 복사됐는지)를 미래의 파인튜닝 원료로 축적한다. 이벤트 규칙상 **멘트 원문은 싣지 않고** 톤과 맥락 enum만 남긴다

AI API 연결 자체가 후순위다. 현재는 `src/lib/llm/contracts.ts`에 계약만 있다: `generateRequestSchema`(꽃 정보에 `meaning_source_id` 필수, 추억은 optional), `generateResponseSchema`(`tones` 정확히 3개 — `RESPONSE_TONE_COUNT = 3`). 3톤 1회 호출·zod 파싱 후 렌더·실패 시 템플릿 폴백이라는 v1 §3.4 규칙은 그대로 유효하다.

**재검토 트리거**: 멘트 채택 데이터가 수천 건 쌓이고, 폴백률·톤 불만이 데이터로 확인될 때.

## 7. KPI·리스크

### 7.1 KPI

**v1 KPI 유지** — 5문항 완료율 60% · 멘트 복사·저장 35% · 카드 공유 15% · 아웃링크 클릭 12%.

**v2 추가 제안 — 이야기 소비 지표.** 본질을 이야기로 재정의한 이상, 이야기가 실제로 읽히는지를 재지 않으면 재정의를 검증할 수 없다.

| 이벤트 | 속성 | 측정 대상 |
|---|---|---|
| `story_view` | `story_type`, `confidence_level` | 결과 도달 대비 설화 열람률 |
| `story_more_click` | `index` | **"다른 이야기" 탐색률** — 이야기 축의 핵심 지표 |
| `story_dwell` | `bucket`(구간 enum) | 이야기를 실제로 읽었는지 vs 스쳤는지 |
| `color_reselect` | `color`, `was_suggested` | 색상 재선택 사용률 = 개인화 체감의 대리 지표 |
| `theme_switch` | `flower` | 랜딩 꽃-테마 전환 = 랜딩 체류의 대리 지표 |
| `msg_copy` | `tone` | (v1 유지) 톤 선호 분포 + **미래 파인튜닝 원료** |

- 목표치는 **지금 정하지 않는다.** 기준선이 없는 상태의 숫자는 근거가 없다. 베타 첫 2주 관측 후 설정한다
- 이벤트 규칙은 v1 §3.8 그대로: **속성은 enum·숫자만.** 이야기 본문·멘트·추억·사과문 원문은 어떤 이벤트에도 싣지 않고, 서버에서 자유 텍스트 속성을 거부한다

### 7.2 리스크

| 리스크 | 내용 | 완화 |
|---|---|---|
| **콘텐츠 검수 병목** | 이야기 1편당 리서치→리텔링→태깅→검수. 꽃 30종 × 3~5편이면 100편 규모 | 꽃 우선순위를 정해 순차 적재(현재 9종). 출처 약한 설화도 `single_source` 라벨로 수용(§1.5f). 공백은 `original`로 메우되 라벨 필수 |
