## 0. Executive Summary

### 한 문장 정의

> **DearBloom은 관계와 상황을 입력하면, 검증된 꽃말·이야기·안전 정보를 바탕으로 어울리는 꽃과 선택 이유, 함께 전할 문장과 구매 방법까지 추천하는 AI 꽃 선물 서비스다.**

### 슬로건

> **하고 싶은 마음부터 고르면, 꽃과 이야기가 그 마음을 전해드립니다.**

### 사용자가 겪는 핵심 문제

꽃을 선물하고 싶은 순간은 많지만, 꽃을 잘 모르는 사용자는 다음을 각각 따로 확인해야 한다.

1. 지금 관계와 상황에 어떤 꽃이 어울리는지
2. 검색한 꽃말이 실제로 신뢰할 수 있는지
3. 색상과 문화권에 따라 의미가 달라지지는 않는지
4. 상대의 취향과 반려동물에게 안전한지
5. 카드에 어떤 말을 적어야 하는지
6. 실제로 어디에서 살 수 있는지

문제는 꽃 정보가 전혀 없다는 것이 아니다. **정보는 많지만, 자신의 마음과 상황에 맞는 하나의 선택으로 연결하기 어렵다는 것**이 핵심이다.

### DearBloom의 해결 방식

```text
관계·상황·취향·추억·안전 조건 입력
                ↓
AI가 자유로운 표현을 구조화된 단서로 해석
                ↓
검증된 꽃말·이야기·안전 데이터와 규칙 엔진이 후보를 판단
                ↓
성격이 다른 꽃 3안 + 추천 이유 + 이야기 + 메시지 제안
                ↓
편지·공유·꽃 조합·구매처 탐색으로 연결
```

### 현재 단계

DearBloom은 아이디어 문서만 존재하는 단계가 아니라, 다음을 포함한 **실제 동작 프로토타입**이 구현된 상태다.

- 관계·상황 기반 꽃 3안 추천
- 여러 사람 각각 추천 및 단체 부케 추천
- 꽃 도감과 366일 탄생화
- 꽃말의 문화권·색상별 갈래
- 수백 편의 설화·역사·문학 이야기
- 반려동물 안전성 필터
- 카드 문구 작성 및 편집
- 비밀 편지
- 꽃 조합기
- 읽을거리·꽃축제 정보
- 꽃 구매처 검색 연결
- 서버 없이도 동작하는 정적 심사용 데모

정확한 콘텐츠 행 수는 계속 갱신되므로 문서의 고정 숫자보다 `npm run seed` 검증 결과를 최종 기준으로 삼는다.

# 1. 문제 인식

## 1.1 사용자가 실제로 마주치는 순간

기념일을 맞은 사용자가 연인에게 꽃을 주려고 한다.

처음에는 “예쁜 꽃을 하나 사면 되겠지”라고 생각한다. 그러나 검색을 시작하면 질문이 늘어난다.

> “장미는 너무 뻔한가?”  
> “프리지아는 우정의 의미라는데 연인에게 줘도 되나?”  
> “노란 꽃은 이별이라는 말도 있던데?”  
> “상대가 고양이를 키우는데 백합은 위험하지 않나?”  
> “꽃만 주면 어색한데 카드에는 뭐라고 쓰지?”  
> “지금 계절에 이 꽃을 실제로 살 수 있나?”

사용자는 꽃말 검색, 블로그 비교, 반려동물 안전 검색, 카드 문구 검색, 꽃집 검색을 반복한다. 꽃 한 다발을 고르는 일이 **상품 탐색이 아니라 여러 번의 판단과 검증 작업**이 된다.

## 1.2 현재 사용 흐름의 불편

| 단계 | 사용자의 행동 | 불편 |
|---|---|---|
| 1. 상황 정리 | 축하·감사·위로·사과 중 어떤 마음인지 생각 | 감정을 꽃 이름으로 바로 바꾸기 어려움 |
| 2. 꽃 탐색 | 쇼핑몰이나 검색엔진에서 꽃 검색 | 상품은 많지만 선택 기준이 부족함 |
| 3. 꽃말 확인 | 여러 블로그·도감 비교 | 출처, 색상, 문화권 차이가 섞여 있음 |
| 4. 적합성 판단 | 상대 성향·관계에 맞는지 판단 | 같은 꽃말도 관계에 따라 부담스럽거나 어색할 수 있음 |
| 5. 안전 확인 | 고양이·강아지·향 민감도 검색 | 별도의 전문 정보가 필요함 |
| 6. 문구 작성 | 카드 문장과 사과·축하 멘트 작성 | 꽃을 골라도 표현의 부담이 남음 |
| 7. 구매 | 판매처·꽃집·가격·계절 확인 | 추천 정보와 실제 구매가 분리돼 있음 |

### 공감 가능한 한 문장

> **꽃을 선물할 때마다 꽃말, 안전성, 카드 문구와 구매처를 따로 찾는 과정이 너무 귀찮다.**

## 1.3 표면적 문제와 본질적 문제

### 표면적 문제

> “어떤 꽃을 줘야 할지 모르겠다.”

### 본질적 문제

> **내가 전하려는 마음에 이 꽃이 정말 맞는지 판단하고 설명할 기준이 없다.**

꽃을 잘 아는지의 문제가 아니다. 사용자는 “더 많은 꽃 이름”보다 다음을 원한다.

- 이 관계에서 부담스럽지 않은가
- 지금 전하려는 마음과 맞는가
- 왜 이 꽃을 골랐다고 말할 수 있는가
- 상대의 취향과 생활환경까지 고려했는가
- 틀린 꽃말이나 위험한 정보를 믿고 있지는 않은가

## 1.4 기존 대안이 충분하지 않은 이유

### 꽃 쇼핑몰

가격, 크기, 색상, 배송 속도와 상품 사진에는 강하다. 그러나 꽃을 잘 모르는 사용자에게 **“왜 이 관계에서 이 상품이어야 하는가”**를 충분히 설명하지 못한다.

### 꽃말 블로그·백과

꽃의 의미를 찾는 데는 도움을 주지만, 관계·상황·취향·안전·구매까지 이어지는 의사결정 흐름이 없다. 같은 꽃의 의미가 색상·문화권·시대별로 달라도 하나의 정답처럼 보일 수 있다.

### 범용 생성형 AI

자유로운 상담과 메시지 생성에는 강하지만, 꽃말 출처와 반려동물 독성처럼 정확성이 필요한 사실까지 생성 답변에 맡기면 오류 위험이 있다.

### 범용 선물 플랫폼

구매 전환과 배송에는 강하지만, 꽃의 문화적 맥락과 안전성, 상대와의 추억을 중심으로 깊게 추천하기는 어렵다.

## 1.5 문제 정의 최종문

> 꽃은 감정을 표현하는 대표적인 선물이지만, 꽃을 잘 모르는 사용자는 자신의 관계와 상황에 어떤 꽃이 적절한지 판단하기 어렵다. 꽃말·색상별 의미·반려동물 안전성·계절·카드 문구·구매처가 서로 다른 서비스에 흩어져 있어, 한 번의 선물을 위해 여러 번 검색하고 다시 판단해야 한다. DearBloom은 이 분절된 과정을 하나로 연결해 사용자가 **꽃을 고르고, 그 이유를 이해하고, 자신의 말로 전달하도록 돕는다.**

# 2. 산업 배경과 기회

## 2.1 산업 문제는 사용자의 문제 뒤에 둔다

DearBloom의 출발점은 “화훼산업을 살리자”가 아니다. 사용자의 실제 불편을 해결하는 것이 먼저다.

다만 사용자의 선택 부담을 줄이고, 감사·위로·응원·사과처럼 더 다양한 일상 상황에 꽃을 연결한다면 결과적으로 다음 효과를 만들 수 있다.

```text
꽃 콘텐츠 발견
→ 의미 이해
→ 개인화 추천
→ 구매 의도 형성
→ 지역 꽃집·판매처 이동
→ 새로운 꽃 소비 맥락 축적
```

## 2.2 확인 가능한 시장 신호

국립원예특작과학원의 원예작물별 생산액 통계에 따르면 국내 화훼류 생산액은 2024년 5,344억 원으로, 2015년 6,298억 원보다 명목 기준 약 15% 낮다. 단기적으로 매년 감소한 것은 아니므로 “계속되는 불황”이라고 단정하기보다, **장기적인 성장 정체와 소비 맥락 확대의 필요성**으로 표현하는 것이 정확하다.[^flower-stats]

농림축산식품부도 경조사·선물 중심의 화훼 소비를 생활용 소비로 전환하고, 꽃 생활문화를 확산하는 방향을 정책 과제로 제시해 왔다.[^mafra-life]

## 2.3 DearBloom이 만드는 기회

| 기존 소비 방식 | DearBloom이 만드는 새로운 맥락 |
|---|---|
| 생일·기념일 중심 | 감사·응원·위로·화해·일상 선물로 확장 |
| 장미·튤립 등 익숙한 꽃 중심 | 이야기와 의미를 통해 다양한 품종 발견 |
| 가격·사진 중심 구매 | 관계·상황·선택 이유 중심 구매 |
| 대형 플랫폼 중심 탐색 | 추천 결과에서 지역 꽃집과 공공 판매처로 연결 |
| 구매 후 관계 종료 | 반응·선호를 다음 추천에 반영하는 관계 기록 |

# 3. 사용자 정의

## 3.1 초기 핵심 타깃

> **꽃을 잘 모르지만, 가까운 사람에게 의미 있고 센스 있는 선물을 하고 싶은 20~30대 모바일 사용자**

성별보다 행동과 상황으로 정의한다.

### 특성

- 꽃을 자주 구매하지 않는다.
- 기념일·사과·감사 상황에서 실패하고 싶지 않다.
- 단순히 예쁜 꽃보다 “왜 이 꽃인지”를 설명하고 싶다.
- 검색에 오래 시간을 쓰고 싶지 않다.
- 카드 문구를 쓰는 것을 부담스러워한다.
- 모바일에서 추천부터 구매까지 빠르게 해결하려 한다.

## 3.2 우선순위별 사용자군

| 우선순위 | 사용자군 | 주요 상황 | 핵심 요구 |
|---:|---|---|---|
| 1 | 연인·배우자에게 선물하는 사람 | 기념일, 사과, 고백, 일상 선물 | 부담 없는 꽃과 진심 어린 문구 |
| 2 | 친구·가족에게 선물하는 사람 | 생일, 위로, 감사, 응원 | 관계에 맞는 자연스러운 의미 |
| 3 | 여러 사람에게 선물하는 사람 | 졸업, 수료, 동아리, 팀 행사 | 사람별 차별화 또는 안전한 단체 부케 |
| 4 | 꽃 이야기를 좋아하는 탐색 사용자 | 탄생화, 문학, 설화, 축제 | 신뢰할 수 있는 깊이 있는 콘텐츠 |
| 5 | 지역 꽃집·선물 서비스 | 고객 상담, 상품 추천, 주문 전환 | 추천 이유와 수요 데이터 |

## 3.3 Jobs To Be Done

### 기능적 Job

> “관계와 상황에 어울리고 실제로 구할 수 있는 꽃을 빠르게 고르고 싶다.”

### 감정적 Job

> “대충 고른 선물이 아니라 상대를 생각해 골랐다는 확신을 얻고 싶다.”

### 사회적 Job

> “센스 있고 진심을 표현할 줄 아는 사람으로 보이고 싶다.”

## 3.4 핵심 페인과 기대 결과

| Pain | Desired Gain |
|---|---|
| 꽃 종류를 몰라 선택이 막힘 | 질문에 답하면 후보가 줄어듦 |
| 꽃말이 서로 달라 불안함 | 출처와 문화권 차이를 확인함 |
| 반려동물 위험 여부를 모름 | 위험 꽃이 추천 전에 제외됨 |
| 문구가 진부하거나 과함 | 관계와 추억에 맞는 표현을 얻음 |
| 여러 명에게 같은 꽃만 주게 됨 | 개인별 다른 꽃 또는 단체 부케를 받음 |
| 추천 후 구매처를 다시 찾음 | 꽃 이름을 들고 판매처로 바로 이동함 |

# 4. 서비스 정의와 가치 제안

## 4.1 서비스 포지셔닝

| 항목 | 정의 |
|---|---|
| 카테고리 | 관계·상황 기반 AI 꽃 선물 컨시어지 |
| 핵심 가치 | 꽃 선택에 필요한 검색과 판단을 하나의 흐름으로 통합 |
| 제품 중심 | 꽃말과 꽃에 얽힌 이야기 |
| 실용 수단 | 추천, 안전 필터, 메시지, 편지, 구매 연결 |
| 장기 방향 | 꽃 콘텐츠와 지역 꽃집을 연결하는 의미 기반 수요 플랫폼 |

## 4.2 핵심 가치 제안

### 사용자에게

> **전하고 싶은 마음을 말하면, 꽃과 선택 이유를 함께 골라준다.**

### 콘텐츠 측면

> **하나의 꽃말을 정답처럼 제시하지 않고, 색상·문화권·시대에 따른 여러 갈래를 출처와 함께 보여준다.**

### 안전 측면

> **반려동물 안전성과 같은 사실은 AI가 추측하지 않고 검증된 데이터로 판단한다.**

### 산업 측면

> **꽃을 살 새로운 이유를 만들고, 그 의도를 실제 지역 꽃집과 판매처로 연결한다.**

## 4.3 제품 원칙

1. **이야기가 중심이고 추천은 이야기로 가는 길이다.**
2. **사실은 데이터에서, AI는 해석과 표현에서 사용한다.**
3. **결과만 주지 않고 왜 추천했는지 설명한다.**
4. **안전 조건은 점수보다 먼저 적용한다.**
5. **꽃보다 마음이 먼저다. 특히 사과는 선물로 대체하지 않는다.**
6. **정보가 없으면 지어내지 않고 없다고 말한다.**
7. **개인적인 추억과 문장 원문은 저장하지 않는 것을 기본으로 한다.**
8. **추천 결과는 구매 압박보다 사용자의 판단을 돕는다.**

## 4.4 하지 않는 것

- AI가 출처 없는 꽃말을 즉석에서 생성하지 않는다.
- AI가 반려동물 독성을 추정하지 않는다.
- 꽃이 사과나 관계 회복을 대신한다고 말하지 않는다.
- 검증되지 않은 명언과 문학 구절을 만들어 내지 않는다.
- 모든 화면에 모든 콘텐츠를 펼쳐 정보 과부하를 만들지 않는다.
- 초기부터 재고와 배송을 직접 운영하지 않는다.

# 5. 핵심 사용자 경험

## 5.1 진입 모드

| 모드 | 사용자 문구 | 제공 결과 |
|---|---|---|
| 한 명에게 | 마음을 전할 한 사람이 있어요 | 성격이 다른 꽃 3안 |
| 여러 명 각각 | 여러 명에게 각자 다른 꽃을 주고 싶어요 | 사람별 추천, 중복 회피 |
| 단체 부케 | 팀·모임에 함께 줄 꽃 한 다발 | 모든 사람의 조건을 교차한 최대 3종 |
| 화해의 꽃 | 먼저 손 내밀고 싶은 날이에요 | 사과 상황 전용 톤과 주의 문구 |

> ⚠ 저장소 대조: 네 모드가 모두 실재하지만 **진입 지점이 표처럼 넷으로 갈라져 있지는 않다.** `/recommend` 위저드는 **한 명 전용**이고(`src/components/flow/Wizard.tsx` 머리말 #20 — "여러 명에게 주는 경우는 이 위저드가 다루지 않는다"), 「여러 명 각각」과 「단체 부케」는 `/groups` **한 화면 안의 토글 두 칸**이다(`MODE_LABELS = ['각각', '단체 부케']`). 「화해의 꽃」은 별도 진입이 아니라 플로우 안 **‘마음’ 카드의 `apology`** 이고(`src/components/flow/labels.ts` — "먼저 손 내밀고 싶을 때"), `/groups` 에서는 같은 이름의 라벨 값으로 있다. 랜딩 상단 내비의 `여러 명에게` 는 2026-08-17 사용자 확정으로 내렸다 — 첫 화면에 진입이 둘이면 무엇이 본류인지 흐려진다는 이유였다.

## 5.2 개인 추천 입력 흐름

한 화면에 하나의 질문만 보여주며 45초 안에 완료하는 것을 목표로 한다.

| 단계 | 질문 | 수집 정보 |
|---:|---|---|
| 1 | 어떤 사이인가요? | 연인, 배우자, 썸, 친구, 가족, 동료 |
| 2 | 어떤 마음인가요? | 사과, 고백, 감사, 축하, 위로, 기념일, 그냥 |
| 3 | 상대는 어떤 분인가요? | 분위기 태그, 선호 색상, 자유 한 줄 |
| 4 | 함께 떠오르는 장면이 있나요? | 추억·에피소드·취향을 자유 서술 |
| 5 | 조심할 게 있나요? | 고양이·강아지, 향 민감, 피하고 싶은 꽃 |
| 6 | 언제, 얼마나 생각하나요? | 전달일, 예산 |

실제 화면의 질문 수는 UX 검증에 따라 5단계로 묶을 수 있으며, 핵심은 입력 필드 개수가 아니라 **부담 없이 맥락을 확보하는 것**이다.

> ⚠ 저장소 대조: 이 절이 열어 둔 그대로 **실제 화면은 이미 5단계다**(`TOTAL_STEPS = 5`, 진행 표시도 "다섯 걸음 중 …"). 표의 여섯 문항이 사라진 것이 아니라 묶였다 — 프리셋이 1·2번을 한 번에 받는다(Wizard 머리말: "§1.5l 개편으로 늘어난 것은 **입력의 폭이지 단계 수가 아니다**"). README 의 화면 경로 표도 `/recommend` 를 "다섯 단계 입력"으로 적고 있다.

## 5.3 결과 화면의 정보 위계

1. **추천 꽃과 대표 꽃말**
2. **왜 이 사람과 상황에 어울리는지**
3. **반려동물·향·계절 주의**
4. **추천 색상과 색상별 의미**
5. **그 꽃에 얽힌 이야기**
6. **함께 전할 메시지**
7. **편지·공유·구매 행동**

### 꽃 3안의 역할

| 안 | 역할 | 사용자가 느끼는 차이 |
|---|---|---|
| 안심 | 관계와 상황에 가장 무난한 선택 | “실패할 가능성이 적다” |
| 의미 | 꽃말과 이야기가 가장 잘 맞는 선택 | “내 마음을 가장 잘 설명한다” |
| 대담 | 취향과 개성을 더 강하게 반영 | “남들과 다른 선택이다” |

## 5.4 대표 사용자 시나리오

### 상황

최근 다툰 연인에게 먼저 사과하고 싶다. 상대는 차분한 분위기와 보라색을 좋아하고 고양이와 함께 산다.

### 흐름

1. 사용자는 ‘먼저 손 내밀고 싶은 날’을 선택한다.
2. 관계, 감정, 상대의 취향과 고양이 동거 여부를 입력한다.
3. “함께 갔던 바닷가에서 보라색 노을을 좋아했다”는 추억을 한 줄 적는다.
4. AI가 자유 서술에서 바다·보라색·차분함 등의 단서를 해석한다.
5. 규칙 엔진이 고양이에게 위험한 꽃을 먼저 제외한다.
6. 남은 후보를 상황·관계·계절·취향·에피소드 기준으로 평가한다.
7. 서로 다른 성격의 꽃 3안과 추천 이유를 제시한다.
8. 사용자는 꽃의 문화권별 의미와 이야기를 읽고 한 꽃을 선택한다.
9. 메시지 제안을 자신의 말투로 수정한다.
10. 꽃집 검색 또는 구매처로 이동하고 비밀 편지 링크를 함께 전달한다.

### 사용자가 얻는 결과

> “예뻐서 골랐어”가 아니라,  
> **“네가 좋아했던 장면과 지금 전하고 싶은 마음을 생각해서 이 꽃을 골랐어”**라고 말할 수 있다.

# 6. 핵심 기능

## 6.1 관계·상황 기반 꽃 추천 **[구현]**

- 관계, 마음, 취향, 예산, 전달일을 반영
- 안전 조건을 먼저 적용
- 상위 점수만 나열하지 않고 세 꽃의 가격대·미감·색이 겹치지 않도록 다양성 보정
- 각 결과에 선택 이유와 주의사항 제공
- 입력하지 않은 정보는 중립으로 처리

## 6.2 자유 서술 AI 해석 **[구현]**

사용자가 “파도 소리를 좋아하는 사람”, “첫눈을 함께 봤다”처럼 엔진 어휘 밖의 문장을 적어도 AI가 다음과 같은 구조화 단서로 변환한다.

- 분위기와 미감
- 색과 자연 이미지
- 상대의 성향
- 실제 반려동물 동거 신호
- 피하고 싶은 꽃 이름
- 추억의 핵심 소재

AI 해석에 실패하거나 API 키가 없으면 로컬 사전 기반 폴백을 사용한다. 최종 추천 판단은 계속 규칙 엔진이 맡는다.

## 6.3 꽃말·이야기 아카이브 **[구현]**

- 문화권별 꽃말
- 색상별 꽃말
- 신화·설화·역사
- 인물과 실화
- 문학 작품 속 꽃
- 창작 이야기는 별도 라벨
- 이야기별 출처와 신뢰 수준
- 꽃별 여러 이야기를 비교 탐색

## 6.4 꽃 도감과 366일 탄생화 **[구현]**

- 꽃 이름과 학명 검색
- 대표 사진과 세밀화
- 날짜별 탄생화 찾기
- 탄생화 이야기
- 꽃말·문학·안전 정보와 연결
- 콘텐츠가 충분하지 않은 꽃은 정식 도감과 사전형 정보를 구분

## 6.5 반려동물 안전 필터 **[구현]**

- 고양이·강아지 안전성 조합 전수 관리
- 심각한 위험은 추천 후보에서 제외
- 경미한 주의는 결과에 명확히 표시
- 단체 부케에서 모든 수신자의 조건을 교차 검사
- “누구의 조건 때문에 제외했는지” 이유 제공

## 6.6 메시지 생성과 편집 **[구현]**

- 짧게 / 보통 길이
- 담백한 / 따뜻한 / 진지한 등 톤 선택
- 추천 꽃과 이야기 맥락 반영
- 자유롭게 고쳐 쓰기
- 새 문장 받기
- 키가 없거나 생성이 실패하면 검증된 템플릿 예문 사용
- 사과 상황에서는 유쾌하게 넘기는 톤을 제한

## 6.7 비밀 편지 **[구현, 저장 방식 제한]**

- 편지 작성·수정
- 번호로 다시 열기
- 현재는 브라우저 `localStorage` 저장
- 같은 브라우저와 프로필에서만 열 수 있음
- 다른 기기 공유를 지원하려면 서버 저장과 만료·권한 설계가 필요

> ⚠ 저장소 대조: `localStorage` 서술은 정확하다. 덧붙이면 **서버 어댑터 코드는 이미 다 있다**(`src/lib/letters/supabase-store.ts`, 마이그레이션 `db/migrations/0009_letters.sql`). 그런데 `createLetterStore()` 는 **env 가 채워져 있어도 `localStorage` 를 돌려준다.** 전환을 막고 있는 것은 저장소 설계가 아니라 **로그인(auth) 부재**다 — 0009 의 소유자 정책이 전부 `auth.uid()` 기준이라 anon 키로는 저장이 거절되고, 로그인 없이 되는 것은 `open_letter(code)` 하나뿐이다. 쓰기용 `save_letter` RPC 도 아직 마이그레이션에 없다(파일 머리말이 0011 후보 계약을 적어 두었다). 그래서 §11.3 이 적은 "다음 조치"의 실제 첫 칸은 서버 저장 자체가 아니라 **익명 로그인을 붙이는 일**이고, 반쪽만 전환하면 "쓰기는 이 기기, 읽기는 서버"가 되어 사용자의 편지가 두 곳으로 갈린다는 것이 미루는 이유다.

## 6.8 여러 사람 추천 **[구현]**

### 개인별 추천

- 최대 인원 제한
- 사람별 취향과 안전 조건 반영
- 가능한 한 꽃 중복 회피

### 단체 부케

- 주 꽃과 곁들이 꽃 구성
- 고양이·강아지 안전성 교차 검사
- 향의 합산 수준 표시
- 꽃말을 한 문장으로 억지로 합치지 않고 나란히 설명
- 데이터로 말할 수 없는 색 조합은 지어내지 않음

## 6.9 읽을거리와 꽃축제 **[구현]**

- 꽃 관련 기사·실용 정보·트렌드·축제
- 계절과 분위기 필터
- 만료된 행사 자동 판정
- 관광공사 API와 큐레이션 데이터 결합
- 관련 꽃 도감과 추천 결과로 연결

> ⚠ 저장소 대조: 맞다. "결합" 의 실제 구조만 적어 두면 — 한국관광공사 TourAPI 산출물은 `content/generated/festivals.json` 으로 굳고, **사람이 직접 열어 본 원장 `content/reads.csv` 와 끝까지 다른 파일로 남는다.** 한 번 섞으면 원장의 약속이 그 자리에서 거짓이 되기 때문이다. 화면은 API 카드에 `한국관광공사 제공` 라벨을 달고, 같은 축제가 양쪽에 있으면 **원장이 이긴다**(`src/lib/data/reads-festivals.ts`). 수집은 `npm run reads:festivals` 가 맡는다.

## 6.10 구매 연결 **[구현, 실상품 연동 제한]**

- 추천 꽃 이름을 들고 네이버쇼핑, 우체국, 카카오 선물하기, 꽃 전문몰 등으로 이동
- 지역의 가까운 꽃집 탐색
- 파트너·공익 판매처 표시
- 실상품 API가 없거나 키가 없으면 판매처 검색 목록으로 폴백
- 가짜 상품 상세나 존재하지 않는 가격을 만들지 않음

> ⚠ 저장소 대조: "실상품 API 가 없거나 키가 없으면 폴백" 보다 현재 상태가 **한 칸 더 세다 — 실상품 공급원이 본배포에도 지금 한 곳도 없다.** 네이버 쇼핑 검색 오픈API 는 2026-08-01 종료됐고, 대체로 붙였던 11번가는 셀러 전용으로 바뀌었으며, 쿠팡 파트너스는 수수료 추적 링크라 「제휴 아님」 고지와 충돌한다(`src/lib/buy/elevenst.ts`, `src/lib/demo/sample-products.ts`). 그래서 구매 경로는 **사실상 언제나 판매처 검색 목록**이다. 화면에 서는 곳은 일곱이다 — 네이버쇼핑 · 우체국 꽃배달 · 우리화원(장애인표준사업장) · 카카오톡 선물하기 · 쿠팡 · 플립플라워 스토어(청각장애 플로리스트) · 꾸까(본문의 "꽃 전문몰" 이 이 자리다). 이 링크들은 전부 **제휴 코드가 붙지 않은 순수 검색 URL** 이다(`src/components/flow/buy-links.ts`). "파트너·공익 판매처 표시" 는 **배지가 아니라 추천순 정렬 점수로만** 반영한다(2026-08-17 사용자 확정 — 화면 어디에도 "공익이라 올렸다"고 적지 않는다).
>
> 마지막 줄의 금지선은 지켜지고 있다. 정적 데모만 예시 목록을 세우되 `sample: true` 표식이 화면에 **① 예시라고 적게 하고 ② 행을 상품 상세가 아니라 그 판매처로 보내게** 강제한다. 본배포에는 이 표식을 켜는 줄이 아예 없다 — 키가 없으면 조용히 빈손이고 화면은 사이트 목록으로 내려간다.

# 7. AI와 추천 시스템 설계

## 7.1 핵심 원칙

> **AI가 꽃을 마음대로 고르는 서비스가 아니라, AI는 사람의 말을 이해하고 검증된 데이터와 규칙 엔진이 꽃을 판단하는 서비스다.**

## 7.2 역할 분리

| 영역 | 담당 | 이유 |
|---|---|---|
| 자유 문장 이해 | LLM + 로컬 폴백 | 사용자가 엔진의 정해진 단어를 몰라도 됨 |
| 꽃말·출처 | 검증 데이터 | 환각과 출처 혼동 방지 |
| 반려동물 안전 | 검증 데이터 + 강제 제외 규칙 | 안전 정보를 생성 모델에 맡기지 않음 |
| 추천 순위 | 순수 규칙 엔진 | 재현 가능하고 설명할 수 있음 |
| 3안 다양성 | 다양성 알고리즘 | 비슷한 결과 세 개가 나오는 문제 방지 |
| 메시지 문체 | LLM 또는 템플릿 | 개인화된 표현 제공 |
| 문학·명언 | 승인된 데이터 | 가짜 인용 방지 |

## 7.3 추천 처리 순서

```text
1. 입력 검증 및 표준화
2. 자유 서술에서 단서 추출
3. 위험·비선호·예산·향 조건으로 강제 제외
4. 관계·마음·계절·취향·에피소드 적합도 평가
5. 상위 후보의 미감·색·가격대 다양성 보정
6. 안심 / 의미 / 대담 역할 배정
7. 규칙 ID를 사람이 읽는 추천 이유로 변환
8. 꽃말·이야기·색상·문학·메시지와 조립
```

## 7.4 설명 가능한 추천

결과 화면은 “AI가 추천했습니다”로 끝나지 않는다.

- 어떤 입력이 반영됐는지
- 어떤 위험 조건 때문에 후보가 제외됐는지
- 어떤 꽃말이나 이야기와 연결됐는지
- 계절상 쉽게 구할 수 있는지
- 왜 세 결과가 서로 다른지

를 사용자에게 설명한다.

## 7.5 안전 장치

- 심각한 관계·안전 상황은 생성 호출 전에 차단
- 반려동물 안전은 AI 추정 금지
- 메시지 결과는 스키마 검증 후 렌더
- 생성 실패 시 템플릿 폴백
- API 키를 브라우저에 노출하지 않음
- 자유 서술에서 제3자의 반려동물을 잘못 감지하지 않도록 반례 테스트
- 개인정보 원문은 로그와 분석 이벤트에 남기지 않음

## 7.6 정적 데모에서의 AI 표현

공모전용 정적 Netlify 데모에는 서버가 없기 때문에 API 키를 넣지 않는다.

- 추천 결과: 본서비스와 같은 규칙 엔진으로 실제 계산
- 꽃말·이야기·안전 정보: 실제 데이터
- 카드 문구: 미리 검토한 예문
- 화면 고지: “지금 보이는 멘트는 미리 적어 둔 예문이에요.”

이는 기능을 속이는 것이 아니라, **API 키 보안과 심사 환경의 안정성을 우선한 의도적인 데모 모드**다.

> ⚠ 저장소 대조: 맞다. "본서비스와 같은 규칙 엔진" 이 어떻게 보장되는지만 덧붙이면 — 데모는 흉내 내는 별도 구현이 아니라 `src/lib/demo/` 의 **쌍둥이 액션**(`recommend-actions.ts` · `groups-actions.ts` · `flowers-actions.ts` · `stories-actions.ts`)이 본서비스 라우트와 **같은 조립 모듈 `app/recommend/build-result.ts` 를 그대로 import** 하는 구조다(그 모듈이 엔진을 부른다). 파일 머리말이 같은 말을 한 줄로 적어 두었다 — "데모라고 다른 꽃이 나오지 않는다." 자유 서술 해석도 데모에서 "꺼진" 것이 아니라 애초에 LLM 호출을 하지 않고 로컬 사전 경로로 간다 — §6.2 폴백 사다리의 맨 끝 칸이 그대로 데모의 기본값이다.

# 8. 데이터·콘텐츠 전략

## 8.1 콘텐츠가 경쟁력인 이유

단순 추천 UI는 쉽게 복제될 수 있다. DearBloom의 장기 자산은 다음을 관계와 상황에 연결한 구조화 데이터다.

- 어떤 꽃말이 어느 문화권과 색상에서 전해지는가
- 그 의미의 출처와 신뢰 수준은 무엇인가
- 어떤 관계와 마음에 잘 맞는가
- 어떤 상황에서는 피해야 하는가
- 고양이·강아지에게 어떤 위험이 있는가
- 어떤 이야기와 문학 작품으로 이어지는가
- 사용자가 어떤 추천 이유를 선택·저장·공유했는가

## 8.2 콘텐츠 유형

| 유형 | 핵심 필드 | 운영 원칙 |
|---|---|---|
| 꽃 기본 정보 | 이름, 학명, 색, 향, 개화월, 미감 | 종과 품종 혼동 방지 |
| 꽃말 | 의미, 문화권, 시대, 색상, 출처 | 하나의 정답으로 합치지 않음 |
| 이야기 | 유형, 지역, 시대, 요약, 전문, 출처, 신뢰 | 사실·전승·창작 구분 |
| 문학·인용 | 저자, 작품, 판본, 저작권 상태 | 승인 목록 밖 생성 금지 |
| 안전성 | 동물 종, 심각도, 증상, 출처 | AI 추정 금지 |
| 추천 규칙 | 관계, 마음, 가점·회피, 근거 | 이유가 직접 말하는 범위만 사용 |
| 메시지 예문 | 마음, 톤, 길이 | 실제 사람이 읽었을 때 자연스러운 문장 |
| 탄생화 | 날짜, 꽃 이름, 의미, 이야기 | 정식 도감과 사전형 데이터 구분 |
| 읽을거리·축제 | 주제, 계절, 지역, 만료일, 링크 | 만료·출처·라이선스 관리 |

> ⚠ 저장소 대조: 아홉 유형이 CSV 원장과 그대로 짝을 이룬다. 실제 파일은 열두 벌이다 — `flowers` · `meanings` · `stories` · `quotes` · `pet_safety` · `rules` · `templates` · `birth_flowers` · `birth_stories` · `birth_photos` · `reads` · `occasions`(`SEED_FILE_KEYS` 가 12 임을 테스트가 못 박는다). 표에 이름이 없는 셋은 탄생화 사진 원장(`birth_photos`), 탄생화 이야기(`birth_stories` — 표의 「탄생화」가 이 둘을 함께 가리킨다), 그리고 상황 예시 원장(`occasions`, 2026-08-18 에 하드코딩 두 벌을 걷어 와 만든 것)이다.

## 8.3 신뢰 라벨

사용자에게 내부 점수나 연구 문서 같은 표현을 그대로 노출하지 않고 이해하기 쉬운 언어로 바꾼다.

| 내부 상태 | 사용자 표현 예시 |

| 문화권마다 다름 | 지역과 시대에 따라 다른 뜻으로 전해져요 |
| 한 출처 또는 드문 전승 | 드물게 전해지는 이야기예요 |
| 창작 | DearBloom이 만든 이야기예요 |
| 출처 부족 | 확인할 수 있는 자료가 충분하지 않아요 |

- 모바일에서 한 화면에 하나의 판단만 요구

# 10. 디자인 방향

## 10.1 컨셉

> **Night Botanical Archive — 밤의 식물 아카이브**

감성적인 꽃 쇼핑몰보다, 오래된 식물 도감과 현대적인 편집 디자인이 만나는 느낌을 지향한다.

- 오늘의 꽃에 따라 테마가 변하지만 정보 구조는 유지

## 10.3 접근성

- 본문 대비 4.5:1 이상 실측

# 11. 기술 아키텍처와 현재 구현

## 11.1 기술 구성

| 영역 | 구성 |
|---|---|
| 프론트·서버 | Next.js App Router, React, TypeScript |
| 추천 엔진 | 프레임워크와 분리된 순수 함수 모듈 |
| 검증 | zod 기반 입력·응답·CSV 스키마 |
| 콘텐츠 | 사람이 검토하는 `content/*.csv` 단일 원본 |
| 데이터베이스 | Supabase/Postgres 마이그레이션과 시드 경로 준비 |
| AI | 서버 전용 다중 프로바이더 + 로컬·템플릿 폴백 |

| CI | lint, typecheck, test, seed, build |

## 11.2 현재 구현 강점

- 외부 DB와 AI 키가 없어도 핵심 화면 확인 가능
- 추천 엔진이 서버와 정적 데모에서 동일하게 동작
- 꽃말·안전·추천 규칙을 콘텐츠와 코드로 분리
- 실패 시 빈 화면 대신 폴백 제공
- 위험·회피 규칙에 대한 회귀 테스트
- 개인정보를 공유 URL과 로그에 넣지 않는 구조
- 이미지와 콘텐츠 라이선스 원장 관리
- 실제 인터랙션과 내부 링크를 감사하는 테스트 체계

## 11.3 현재 제한과 해결 계획

| 제한 | 현재 상태 | 다음 조치 |
|---|---|---|
| 콘텐츠 런타임 | CSV가 실제 조회 원본 | 사용자 검증 후 Supabase 런타임 전환 판단 |
| 비밀 편지 | `localStorage`, 같은 기기만 열림 | 만료·권한이 있는 서버 저장 또는 공유 방식 재설계 |
| 실상품 가격 | 안정적인 공개 상품 API 부족 | 지역 꽃집 재고·가격 입력 또는 파트너 피드 파일럿 |
| 계절 가용성 | 개화월과 일반 규칙 중심 | 지역·도매시장·꽃집 실제 가능 여부 반영 |
| AI 비용·지연 | 외부 API 의존 | 캐시, 프롬프트 축소, 폴백률 계측 |
| 추천 품질 | 규칙과 콘텐츠 근거는 충분, 실제 만족 데이터 부족 | 사용자 선택·반응 데이터로 가중치 개선 |
| 정보량 | 콘텐츠가 많아 결과 화면이 길어질 수 있음 | 단계적 공개와 핵심 행동 중심 재조판 |

> ⚠ 저장소 대조: CI 행은 `.github/workflows/ci.yml` 과 정확히 같다(`npm ci → lint → typecheck → test → seed → build`, Node 24). 손볼 곳은 **배포 행**이다 — Vercel·Netlify 는 준비된 경로일 뿐 **본배포 도메인이 아직 없다.** `NEXT_PUBLIC_SITE_URL` 이 비어 있으면 `SITE_URL` 이 `http://localhost:3000` 으로 떨어지고(`src/lib/site.ts` — "가짜 도메인을 상수로 박지 않는다"), 그 한 값이 canonical · OG · sitemap 셋을 함께 끌고 간다. 같은 이유로 Supabase 도 미연결이다. 즉 §11.3 「콘텐츠 런타임」 행이 말하는 상태가 곧 지금이고, 배포는 **환경변수 한 줄로 열리는 스위치**로 남아 있다. 저장소에 실제로 있는 배포 산출물은 정적 데모 패키지뿐이다(`deploy/dearbloom-static-demo-2026-08-19.zip`).
>
> 검증 명령 하나에 함정이 있어 적어 둔다. **`npm run typecheck` 는 `.next/` 가 없는 상태에서 실패한다** — `tsconfig.json` 이 `.next/types/**/*.ts` 를 include 하는데 Next 가 생성하는 `PageProps` · `LayoutProps` 전역이 그 안에 있어서다(`Cannot find name 'PageProps'`). `npm run build` 나 `npm run dev` 를 한 번 돌리면 사라진다. `npm run build:static` 이 데모용 `.next/` 를 지우므로 **정적 데모를 만든 직후에 특히 자주 만난다.** CI 는 매번 새로 `npm ci` 부터 도는데도 통과하는데, 그 순서(`typecheck` 가 `build` 앞)를 감안하면 이 함정은 로컬 상태에 따라 갈리는 자리다 — 커밋 전 검증에서 이 오류를 보면 코드가 아니라 `.next/` 부재를 먼저 의심하라.

# 13. 비즈니스 모델

## 13.1 단계별 수익 구조

| 단계 | 모델 | 설명 |
|---:|---|---|
| 1 | 제휴·검색 전환 | 추천 꽃을 판매처와 지역 꽃집으로 연결하고 전환 수익 확보 |
| 2 | 꽃집 리드·예약 | 지역·수령일·예산을 포함한 구매 의향 고객 전달 |
| 3 | 꽃집용 추천 도구 | 상담 입력 → 꽃·근거·카드 문구를 만드는 B2B 도구 |
| 4 | 추천 위젯·API | 선물 플랫폼과 꽃 쇼핑몰에 의미 기반 추천 제공 |
| 5 | 개인 프리미엄 | 관계 기록, 기념일 알림, 선물 이력, 고급 편지 테마 |
| 6 | 수요 인사이트 | 익명화된 관계·상황·계절별 수요 리포트 |

> ⚠ 저장소 대조: 1단계의 전제인 「제휴·검색 전환」은 지금 **수익 배관이 붙어 있지 않다.** §6.10 각주대로 공급원이 없고, 현재 링크는 제휴 코드가 붙지 않은 순수 검색 URL 이다. 실제로 쿠팡 파트너스는 "수수료 추적 링크" 라는 이유로 한 번 기각된 선택지다 — §13.3 의 「제휴 여부와 외부 이동을 명확히 고지」 원칙이 그 판단의 근거였다. 1단계를 켜는 일은 기술 연동이 아니라 **그 원칙을 어떻게 지키며 붙일 것인가**의 결정에 걸려 있다.

## 13.2 초기에는 직접 재고를 갖지 않는 이유

- 꽃은 지역과 계절에 따라 가용성이 크게 변함
- 폐기와 배송 품질 관리 비용이 높음
- 현재 DearBloom의 강점은 콘텐츠와 추천
- 기존 꽃집의 공급 역량을 활용하는 편이 빠르고 현실적임

## 13.3 거래 원칙

- 광고나 제휴 때문에 안전·적합성이 낮은 꽃을 상위에 올리지 않음
- 추천 점수와 상업적 노출을 분리
- 제휴 여부와 외부 이동을 명확히 고지
- 가격 정보가 없으면 임의 생성하지 않음

# 15. 핵심 성과지표

## 15.1 North Star Metric

> **추천을 완료한 사용자가 꽃의 의미를 확인한 뒤 저장·공유·편지·구매 중 하나의 행동을 수행한 비율**

단순 방문보다 “추천이 실제 선택과 표현을 만들었는가”를 본다.

## 15.2 퍼널 지표

| 단계 | 지표 | 초기 가설 목표 |
|---|---|---:|
| 유입 | 랜딩 → 추천 시작률 | 30% 이상 |
| 입력 | 추천 플로우 완료율 | 60% 이상 |
| 품질 | 추천 적합도 평가 | 4.0/5 이상 |
| 이해 | 추천 이유 펼침·이야기 열람률 | 30% 이상 |
| 표현 | 메시지 복사·수정·편지 작성률 | 20% 이상 |
| 확산 | 저장·공유율 | 15% 이상 |
| 전환 | 구매처·꽃집 이동률 | 10% 이상 |
| 반복 | 90일 내 재방문률 | 15% 이상 |
| 신뢰 | 안전·꽃말 오류 신고율 | 1% 미만 |

위 수치는 성과가 아니라 **검증을 위한 초기 가설**이다.

- `recommend_start`

- `result_select{role}`
- `reason_expand`

- `message_copy{tone,length}`

# 16. 검증 계획

## 16.1 가장 먼저 검증할 가설

### 가설 A — 문제 공감

> 꽃을 가끔 구매하는 사용자는 꽃 자체보다 선택 기준과 표현 과정에서 더 큰 불편을 느낀다.

**방법:** 10~15명 인터뷰, 최근 꽃 구매·포기 경험 재구성  
**통과 기준:** 절반 이상이 꽃말·문구·안전·구매처 중 두 개 이상을 별도로 검색

### 가설 B — 추천 가치

> 꽃 이름만 보여주는 것보다 선택 이유를 제공할 때 추천 신뢰가 높아진다.

**방법:** 이유 없는 결과 vs 이유 있는 결과 비교  
**통과 기준:** 이유 있는 결과의 선택 확신 점수가 유의하게 높음

### 가설 C — 이야기의 역할

> 사용자는 추천된 꽃의 이야기를 읽을 때 더 의미 있다고 느끼고 공유할 가능성이 높아진다.

**방법:** 이야기 블록 노출 A/B  
**통과 기준:** 저장·공유 또는 메시지 복사율 상승

### 가설 D — 안전 기능

> 반려동물 안전 필터는 특정 사용자에게 강한 차별점과 재방문 이유가 된다.

**방법:** 반려동물 보유 사용자 5명 이상 과업 테스트  
**통과 기준:** 안전 필터를 핵심 신뢰 이유로 언급

### 가설 E — 구매 연결

> 추천 결과에서 꽃 이름과 구매 문구를 그대로 넘겨주면 실제 구매 탐색이 쉬워진다.

**방법:** 검색 링크 vs 일반 꽃집 링크 비교  
**통과 기준:** 검색 성공 시간과 이탈률 감소

## 16.2 인터뷰 질문

1. 마지막으로 꽃을 사거나 사려다 포기한 상황은 언제였나요?
2. 어떤 기준으로 꽃을 골랐나요?
3. 꽃말을 검색했다면 어디에서 무엇을 확인했나요?
4. 검색 결과가 달랐을 때 어떻게 판단했나요?
5. 카드 문구를 직접 썼나요, 예문을 찾았나요?
6. 상대의 반려동물이나 향 민감도를 생각한 적이 있나요?
7. DearBloom 결과에서 가장 믿음이 가는 부분과 불필요한 부분은 무엇인가요?
8. 추천 후 바로 꽃을 사고 싶다면 어떤 정보가 더 필요하나요?

> ⚠ 저장소 대조: 가설 B·C 는 **A/B 실험 장치를 전제**하는데 저장소에 그 갈래(분기 노출·할당·기록)가 없다. §15 각주의 이벤트 부재와 같은 뿌리다. 반면 가설 D 는 지금 그대로 과업 테스트가 가능하다 — 반려동물 안전 필터는 데이터(`content/pet_safety.csv` 59종 × 2)와 강제 제외 규칙이 이미 서 있고 정적 데모에서도 동일하게 동작한다. 가설 E 의 "검색 링크" 도 지금 화면에 실재하는 일곱 판매처 링크로 바로 잴 수 있다. **즉 D·E 는 지금, B·C 는 계측을 붙인 뒤다.**

# 18. 위험과 대응

| 위험 | 설명 | 대응 |
|---|---|---|
| 꽃말의 절대화 | 문화권과 시대에 따라 의미가 다름 | 갈래와 출처를 함께 표시 |
| AI 환각 | 꽃말·명언·안전 정보를 지어낼 수 있음 | 사실은 승인 DB에서만 제공 |
| 반려동물 안전 오류 | 실제 건강 피해 가능 | 전문 출처, 강제 제외, 오류 신고 |
| 계절·재고 불일치 | 추천 꽃을 당장 구하지 못할 수 있음 | 가용성 안내, 대체 꽃, 꽃집 확인 |
| 정보 과부하 | 결과 화면이 길고 복잡해짐 | 단계적 공개, 한 안만 우선 전개 |
| 감정의 상업화 | 사과를 선물로 해결하는 인상 | “꽃보다 마음이 먼저” 원칙 |
| 개인정보 노출 | 추억·편지에 민감 정보 포함 | 원문 비저장, 최소 공유 payload |
| API 비용·장애 | 생성이 느리거나 실패 | 다중 폴백, 템플릿, 시간 제한 |
| 이미지·문학 저작권 | 무단 사용 위험 | 승인 원장, 라이선스와 판본 관리 |
| 추천과 광고 충돌 | 제휴 상품이 추천을 왜곡 | 추천 점수와 상업 노출 분리 |

> ⚠ 저장소 대조: 「API 비용·장애」의 대응이 코드에 그대로 있다 — 자유 서술 해석은 **4초**, 멘트 생성은 **10초**의 **서로 다른** 예산을 쓰고(합쳐지지 않는다), 실패하면 각각 로컬 사전과 템플릿 예문으로 내려간다. 추출에 짧은 예산을 준 것은 그 시간이 **사용자가 빈 화면을 보는 시간에 그대로 더해지기** 때문이다(멘트는 결과 화면이 이미 선 뒤에 흘러 들어온다). 「오류 신고」 창구는 §15.3 의 `error_report` 이벤트에 걸려 있어 계측과 함께 열린다.

# 19. 발표·소개 문구

## 19.1 10초 소개

> **DearBloom은 전하고 싶은 마음을 입력하면, 검증된 꽃말과 이야기를 바탕으로 꽃과 선택 이유, 함께 전할 문장까지 골라주는 서비스입니다.**

## 19.2 30초 소개

> 꽃을 선물하려고 하면 꽃말, 색상 의미, 반려동물 안전성, 카드 문구와 구매처를 모두 따로 찾아야 합니다. DearBloom은 관계와 상황, 상대의 취향과 추억을 이해해 어울리는 꽃 세 가지를 제안하고, 왜 이 꽃인지 설명합니다. 사실과 안전성은 검증된 데이터가 판단하고, AI는 사용자의 자유로운 말을 해석하고 자연스러운 문장을 만드는 데 사용합니다.

## 19.3 한 줄 차별성

> **꽃을 추천하는 AI가 아니라, 마음을 이해한 AI와 검증된 꽃 데이터가 함께 판단하는 서비스**

## 19.4 산업 가치 한 줄

> **꽃을 살 새로운 일상적 이유를 만들고, 그 의도를 실제 꽃집으로 연결한다.**

# 20. 의사결정 요약

DearBloom은 다음 논리를 끝까지 유지한다.

```text
꽃을 고르기 어렵다
→ 정보가 없어서가 아니라 내 상황에 맞게 연결되지 않기 때문이다
→ AI가 자유로운 상황과 추억을 이해한다
→ 검증된 데이터와 규칙 엔진이 안전하고 설명 가능한 꽃을 판단한다
→ 사용자는 꽃의 의미와 선택 이유를 이해한다
→ 메시지·편지·구매 행동으로 이어진다
→ 일상 속 새로운 꽃 소비 맥락과 지역 꽃집 유입이 만들어진다
```
